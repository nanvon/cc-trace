# CC Trace 性能与功耗优化方案

> 状态：待实施的专项方案，不代表代码已经优化或性能已经验证  
> 基线日期：2026-08-13  
> 适用版本：当前 `0.1.x` 实现  
> 范围：Rust 后台调度、本地用量扫描、SQLite、Tauri/WebView 与 Vue 查询渲染  
> 本文不拥有产品功能、统计口径、状态语义或参数基线；冲突时仍以各事实所有者文档为准

## 1. 先回答三个问题

### 1.1 需要优化吗？

**需要，但应分阶段优化，不应一次性重写。**

当前实现已经具备共享 HTTP Client、Provider 独立退避、扫描单飞、JSONL 字节水位、SQLite
WAL、只读查询连接和前端请求竞态保护，整体方向正确。静态代码审查仍发现两类会随历史数据
增长而放大的后台成本：

1. SQLite 每次打开写连接都执行 `PRAGMA quick_check`；扫描按批提交时会反复触发完整性检查。
2. 固定 5 分钟扫描虽不重读未变化 JSONL 正文，但仍遍历全部历史文件、校验短前缀、完整读取
   两个标题索引；OpenCode 还会在每轮扫描中计算整张 `part` 表的首条记录。

这些路径属于常驻应用的周期性工作。数据量小时可能不明显，历史会话增多后，CPU 时间、磁盘
读取、线程唤醒和电池消耗都会增长。因此不能只以“目前日常使用正常”判断没有优化必要。

### 1.2 现在就有必要全部做吗？

**没有必要全部做。** 优先级如下：

| 结论 | 项目 | 原因 |
|---|---|---|
| 必须优先验证并优化 | SQLite 写连接反复 `quick_check` | 成本可能随数据库体积和扫描批次数共同放大；不影响业务口径即可消除 |
| 必须优先验证并优化 | OpenCode 每轮全表标题查询 | 即使无新增消息仍可能扫描整张 `part` 表；有明确的增量收窄路径 |
| 应当优化 | 标题索引重复完整读取 | 可按文件身份缓存，保持标题优先级和清理规则不变 |
| 应当优化 | 隐藏主窗口启动即查询 Dashboard | 用户未打开主窗口也会发起最多 10 个聚合查询 |
| 应当优化 | 隐藏紧凑 WebView 的永久秒级时钟 | UI 只要求刷新后 1 分钟内读秒，不要求隐藏期间持续每秒唤醒 |
| 低风险顺手项 | 两个 Statuspage 请求改为并发 | 不改变接口、周期、失败隔离或展示，仅缩短一次网络活跃窗口 |
| 先测再决定 | 全目录遍历与每文件前缀校验 | 它承担新增文件发现和同尺寸改写检测，直接跳过会损伤完整性 |
| 先测再决定 | Dashboard 合并 command／SQL | 能降低查询扇出，但会扩大 Rust/TypeScript 契约改动面 |
| 暂不建议 | 两个 Provider 缓存写合并 | 延迟写入可能降低崩溃后的快照恢复新鲜度，收益需实测证明 |

### 1.3 会影响当前功能吗？

**本方案的目标是用户可见功能与数据结果零变化。** 但“性能优化”不天然安全；扫描、缓存、
数据库恢复和计时器都可能因错误优化产生漏数据或状态不及时。因此每一项都必须满足本文的
功能等价门禁，未通过就不合并。

以下内容不允许作为性能优化的代价：

- 不减少 Codex、Claude Code、Pi、OpenCode 任一数据源。
- 不延长已确认的额度自动刷新候选值、默认值、本地用量 5 分钟扫描或服务状态 5 分钟轮询。
- 不跳过短会话、末尾完整行、刚创建文件、归档文件或上游覆盖／截断检测。
- 不改变六维 Token、Fast 等效 Token、API 等值费用、Pi／OpenCode 官方 `cost`、本地归日或
  缓存命中率口径。
- 不改变 `source + dedup_key` 去重、文件水位、取消续扫、事务提交或重建语义。
- 不改变三维额度状态、Provider 隔离、退避、快照保留、身份变化和 Statuspage 独立状态链。
- 不降低数据库损坏发现、`quota_events` 尽力恢复、原子缓存写入和秘密不落盘的安全边界。
- 不以关闭动效、隐藏加载反馈或让界面少更新来伪装性能改善；用户要求的刷新后 1 分钟读秒仍保留。

## 4. 当前负载模型

### 4.1 常驻后台周期

| 工作 | 当前周期／触发 | 主要资源 |
|---|---|---|
| Codex 额度刷新 | 默认 2 分钟，候选 1/2/3/5/10 分钟，±10% 抖动 | 网络、少量凭据文件读取、缓存写入 |
| Claude Code 额度刷新 | 同上，Provider 独立 | 网络、凭据/Keychain、缓存写入 |
| 本地用量扫描 | 完成引导后立即，之后每 5 分钟 | 目录枚举、文件 metadata/前缀读取、JSON 解析、SQLite |
| Statuspage | 启动立即，之后每 5 分钟；手动整体刷新附带一次 | 两个 HTTP 请求 |
| 唤醒检测 | 每 30 秒采样墙钟 | 极低 CPU，但产生周期唤醒 |
| 紧凑面板用量状态 | 面板聚焦时每 1 秒轮询 | IPC；只在可见交互期存在 |
| 相对时间 | 分钟级；最近刷新 1 分钟内秒级 | WebView 定时器与局部 Vue 更新 |

周期本身属于已确认产品行为，本方案优先减少每轮“做多少无效工作”，不靠延长周期降低功耗。

### 4.2 本地用量扫描调用链

```text
start_auto_usage_scan
  -> UsageService::start_default_scan
  -> 独立阻塞线程 run_scan
  -> initialize usage.db
  -> 读取已知价格与标题索引
  -> 递归发现 Codex / Claude / Pi JSONL
  -> 一次读取全部 scan_files 水位
  -> 每文件 metadata + 前缀 SHA-256 + 必要时增量解析
  -> 每 2000 行或 8 MiB commit_scan_batch
  -> OpenCode watermark 增量查询 + part 标题查询
  -> 缺价检查／必要时在线目录刷新与重计价
```

准确性保护集中在这条链路中。优化不能绕开 prefix、cursor、唯一索引、事务或 active/pending
价格边界，只能消除可以证明不影响结果的重复工作。

### 4.3 主窗口查询扇出

全部四源可见且当前区间有 previous 时，`loadDashboard` 当前最多发起：

```text
1  当前区间 source 汇总
1  上一等长区间 source 汇总
4  chart 区间按 source 的 day 汇总
4  当前区间按 source 的 model 汇总
= 10 次 usage_get_summary
```

每个 command 都新建一个 SQLite 只读连接。主窗口又是预创建的隐藏窗口，根路由挂载后就会
加载 Dashboard，因此启动阶段可能在用户没有打开主窗口时执行这组查询。

## 5. 发现与风险分级

### 5.1 P1：写连接反复执行全库 `quick_check`

当前证据：

- `src-tauri/src/storage/usage_db.rs::open_write`：已有数据库每次打开写连接都执行
  `PRAGMA quick_check`。
- `commit_scan_batch`：每个扫描批次获取写锁后重新调用 `open_write`。
- `record_quota_snapshot`：每个 Provider 成功刷新后也重新调用 `open_write`。

问题不是 `quick_check` 本身，而是执行位置。完整性检查适合初始化、异常恢复和诊断，不适合
每个小事务前重复执行。数据库越大、扫描批次越多，重复读取越明显。

功能风险：如果简单删除检查，运行期间发生数据库损坏时可能失去现有自动恢复入口。因此必须
把“检查频率下降”和“错误触发恢复”一起设计，不能只删一行。

### 5.2 P1：OpenCode 无增量的全表标题计算

当前证据：

- `scan_opencode` 先读取 watermark 之后的 message。
- 同一轮无条件调用 `load_part_titles`。
- `load_part_titles` 对整张 `part` 表执行 `ROW_NUMBER() OVER (PARTITION BY session_id ...)`。

message 查询是增量的，标题查询却不是。即使本轮没有新增 message，仍可能扫描和排序整个
`part` 表。OpenCode 历史增大后，这会成为固定 5 分钟成本。

功能风险：标题规则非常具体——只取每个会话 `(time_created, id)` 最早的一条 part，且首条
不是 text 时不继续找下一条。优化查询必须完整保留这一语义。

### 5.3 P1：周期扫描对历史规模线性增长

当前证据：

- 每轮递归枚举 Codex active/archived、Claude projects、Pi sessions。
- Codex active/archived 重复候选比较时读取 metadata。
- 每个已索引 JSONL 在判断“完全未变化”之前读取最多 4 KiB 并计算 SHA-256。
- `session_index.jsonl` 与 `history.jsonl` 每轮使用 `read_to_string` 完整读取和解析。

正文增量协议是正确的，但无变化轮次仍是 `O(历史文件数 + 标题索引大小)`。

功能风险：目录遍历承担新文件发现，prefix 承担同尺寸改写、截断和覆盖检测。仅凭 mtime/size
跳过、改成纯文件监听或只扫最近文件，都会改变完整性，不允许直接实施。

### 5.4 P2：隐藏主窗口执行 Dashboard 查询和图表准备

当前证据：

- Tauri 在启动时预创建 `main`、`compact`、`onboarding` 三个 WebViewWindow，初始均可隐藏。
- `main` 的默认 URL 是根路由。
- `MainView` 挂载后立即调用 `usage.loadDashboard`，没有先判断窗口是否真正可见。
- Router 当前静态导入全部页面，三个 WebView 都需要解析共享入口及其静态依赖。

后台查询与图表准备应由“用户打开主窗口”触发，而不是“隐藏 WebView 已创建”触发。

功能风险：延迟加载不能让主窗口打开后出现永久空白，也不能破坏外部入口导航、范围共享、
设置返回或数据源过滤。需要显式的一次性可见事件和请求竞态保护。

### 5.5 P2：秒级 ticker 生命周期比产品语义更长

当前证据：

- `useTimeText` 每次调用都会同时订阅分钟级和秒级 ticker。
- `ProviderLane`、`QuotaProgress` 等只需要分钟级方法，也会间接成为秒级 ticker consumer。
- `refreshed` 超过 1 分钟后虽然使用分钟级值格式化，但仍先读取 `nowSeconds` 计算 elapsed。
- Tauri 隐藏窗口不会卸载 Vue 组件，计时器可能继续存在。

产品语义只要求最近刷新后的 1 分钟窗口读秒。隐藏期间或超过 1 分钟后永久每秒 tick 没有用户
价值。

功能风险：不能删掉 `32s 前已刷新`，也不能让重新打开面板时显示冻结时间。

### 5.6 P2：Statuspage 两个请求实际串行

`refresh_service_status` 的注释写两个请求并发，但实现先 await OpenAI，再 await Anthropic。
正常网络下影响有限；网络异常时两个 15 秒超时可能串联，延长一次网络活跃窗口。

改为并发不改变固定 5 分钟周期、失败保留旧值、单源隔离或事件契约，属于低风险优化。

### 5.7 P2：交互查询存在可消除的重复工作

- Conversations 的搜索、防抖、排序和项目选择都会同时重载列表与项目选项。
- 项目选项 SQL 并不使用 search、sort 或当前 project，部分触发属于无效查询。
- Dashboard 多条 SQL 对同一区间重复扫描 `usage_entries`；是否值得合并需用真实规模验证。

这些主要影响主窗口使用时的响应和短时 CPU，不是隐藏常驻功耗的第一优先级。

### 5.8 P3：额度缓存相邻写入与 `fsync`

两个 Provider 独立完成时都会保存完整 `quota-cache.json`，保存过程包含临时文件、`sync_all` 和
原子 rename。它保证了每个 Provider 成功后都尽快形成可恢复快照，可靠性高于少一次写盘。

除非真实采样证明它是显著热点，否则不建议为了合并两次写入而延迟落盘。可以先做“相同内容
不写”的无损判定；但 `last_success_at`、`captured_at` 正常变化时仍应保存。

## 6. 优化总原则

1. **先证明结果相同，再比较速度。** 性能数字不能覆盖统计不一致。
2. **优先消除重复工作，不改变工作频率。** 参数基线保持不变。
3. **不以概率正确替代确定性正确。** 文件监听、mtime、缓存只能加速，不能成为漏扫时无兜底的
   唯一事实源。
4. **不新增第二套数据源。** 前端不缓存一套独立统计，系统区域不重新计算额度。
5. **不为了吞吐阻塞交互。** 扫描继续在阻塞线程，Provider 网络继续异步；SQLite 写锁内不做
   不必要的网络、长时间等待或 UI IPC。
6. **无实测收益不引入复杂度。** 一项优化若只降低不可测噪声，却增加恢复和竞态路径，应放弃。
7. **逐项提交、逐项可回退。** 不把数据库、扫描、UI 生命周期和网络优化混进一个提交。

## 7. 分阶段实施方案

### 阶段 0：建立可复现基线

#### 目标

在改代码前建立“结果基线”和“资源基线”，防止优化后只能凭体感判断。

#### 数据集

使用脱敏 Fixture 派生四档规模，不读取真实用户目录：

| 数据集 | 用途 |
|---|---|
| S | 当前单测 Fixture；快速正确性回归 |
| M | 数百文件、数万条完整行；模拟普通长期使用 |
| L | 数千文件、数十万条完整行；观察历史规模增长 |
| R | 截断、同尺寸改写、归档重复、半行、超长行、无效 JSON、OpenCode 首 part 非 text |

M/L 只机械复制并改写脱敏 ID 与时间，不能引入真实标题、路径、账号或消息正文。

#### 场景

| 场景 | 操作 | 主要观察 |
|---|---|---|
| B0 | 应用隐藏常驻 30 分钟，无新数据 | CPU time、wakeups、磁盘 I/O、网络次数 |
| B1 | 完成一次全量重建 | 总耗时、CPU time、峰值 RSS、批次数、`quick_check` 次数 |
| B2 | 连续 5 次无变化自动扫描 | 每轮耗时、读取字节、文件打开数、数据库读取 |
| B3 | 仅一个 JSONL 追加一条完整事实 | 增量延迟、读取字节、入库结果 |
| B4 | JSONL 截断／覆盖／同尺寸改写 | 旧事实替换、offset、去重、对话元数据 |
| B5 | OpenCode 无新增／少量新增／全量重建 | message 与 part 查询耗时、扫描行数 |
| B6 | 应用启动但不打开主窗口 | SQLite query 次数、ECharts/前端 CPU、RSS |
| B7 | 打开紧凑面板 2 分钟再隐藏 | 秒级 ticker 生命周期、IPC、Vue update |
| B8 | 打开用量／对话／时间线并切换筛选 | 查询次数、P50/P95 响应时间、结果一致性 |

#### 采集指标

- 进程 CPU time，而不是单点 CPU 百分比。
- 唤醒次数／秒与定时器触发次数。
- 读取、写入字节和文件打开次数。
- 扫描总耗时、每文件耗时、每批提交耗时。
- SQLite statement 次数、`quick_check` 次数、查询计划与慢查询。
- WebView 主线程长任务、Vue 更新次数和图表 resize 次数。
- 峰值与稳定态 RSS。
- macOS Energy Impact／Instruments Energy Log；Windows 使用 ETW/WPA 或等价工具。

> 平台结论必须分别记录。macOS 数据不能推断 Windows WebView2 和文件系统行为。

#### 基线结果文件

性能原始数据不写入规范文档。实施时新增带日期、平台、构建类型、数据集版本和命令的验证记录；
只记录脱敏汇总，不提交真实路径、标题或数据库内容。

### 阶段 1：收敛 SQLite 完整性检查

#### 推荐设计

把当前 `open_write` 拆成三个职责明确的路径，并先采用保守的“两级检查”：

```text
initialize_once
  -> 创建目录／打开连接
  -> 已有库执行一次 quick_check
  -> 校验 user_version／迁移
  -> 设置 WAL、synchronous、foreign_keys
  -> initialized = true

open_write_connection
  -> 打开连接
  -> busy_timeout
  -> WAL / synchronous / foreign_keys
  -> 不重复 quick_check，不重复迁移

verify_logical_write
  -> 一次完整扫描、一次重计价、一次重建或一次额度历史写入完成后执行 quick_check
  -> 扫描的 2000 行 / 8 MiB 批次只是同一逻辑操作的事务边界，不逐批重复全库检查

recover_after_corruption
  -> SQLite 明确报告损坏／非数据库，或任一 quick_check 失败时触发
  -> 仍执行 quota_events 尽力导出、文件组保留和重建
```

不建议建立永久连接作为第一步：当前“短连接 + 进程内写锁”边界简单可靠，先消除重复
`quick_check` 就能验证主要收益，没必要同时扩大连接生命周期和 Send/Sync 风险。

这一步只消除扫描批次放大的重复检查，不取消逻辑写操作后的健康检查。若实测显示两分钟额度
历史写入后的检查仍是主要热点，再单独讨论“固定健康检查 cadence + SQLite 错误即时恢复”；它会
改变潜在损坏的主动发现时机，必须另行取得产品所有者同意并同步规范，不能在本阶段默认采用。

#### 必须保留

- 首次打开已有库与每个逻辑写操作完成后仍执行 `quick_check`。
- schema 过高仍拒绝写入，低版本仍在单事务迁移。
- WAL、`synchronous=NORMAL`、`foreign_keys=ON`、5 秒 busy timeout 不变。
- 损坏文件组保留、`quota_events` 尽力恢复不变。
- 任一事务失败时不得推进扫描水位。
- 普通 SQL/I/O 错误不能一律当作损坏并重建。

#### 定向验证

- 记录一次全量扫描的写批次数与 `quick_check` 次数：无论扫描产生多少批次，本轮扫描只在
  初始化和扫描逻辑操作完成边界检查，不按批次数线性增加。
- 构造启动前损坏库，确认恢复路径与现行结果完全一致。
- 构造运行中返回 `SQLITE_CORRUPT`／`SQLITE_NOTADB` 的路径，确认进入一次受写锁保护的恢复，
  不形成恢复循环。
- 扫描批次、重计价和额度历史并发时，仍只有一个逻辑写者。

#### 回退

该阶段不改 schema、不改 command。失败时可独立恢复原 `open_write`，不会产生不可逆数据迁移。

### 阶段 2：收窄 OpenCode 标题查询

#### 推荐设计

把流程改为“先得到本轮候选 session，再只查这些 session 的首 part”：

1. 读取 `message.time_created >= watermark`，仍按 `(time_created, id)` 排序。
2. 应用现有 seen 去重；收集本轮真正需要处理的 assistant message。
3. 仅对 `session.title` 为空、且本轮需要生成/更新 conversation 的 session id 查询首 part。
4. session id 分块绑定参数，不能把 ID 拼进 SQL；每块不超过 SQLite 参数上限。
5. 查询仍严格取 `(time_created, id)` 第一条 part；第一条不是 text 时返回无标题，不继续找。
6. 按现有规则清理、截 80 字符并写入同一 `conversations` UPSERT。

也可使用只覆盖候选 session 的 CTE/window query，但不推荐对每条 message 使用相关子查询，避免
同一 session 多条新增消息重复扫描 part。

#### 同步的小优化

`seen_order` 超过 20,000 时当前循环反复 `Vec::remove(0)`。改为一次 `drain` 或 `VecDeque`，
只改变内存移动成本，不改变保留最近 20,000 个 ID 的顺序和内容。

#### 必须保留

- watermark 仍为 `max(message.time_created)`，查询仍使用 `>=`。
- seen ID 上限与最近顺序不变，唯一索引仍是最终去重边界。
- user 模型继承、assistant 顶层优先、零费用跳过、reasoning 并入 output 的规则不变。
- 官方 `cost` 总额、`pricing_fingerprint = NULL` 和不参与在线补价不变。
- OpenCode 库缺失、打不开或 schema 不兼容仍 no-op，不升级为全局扫描失败。
- 只读打开上游数据库，不写 OpenCode 的任何表。

#### 定向验证

- 无新增消息时不查询整张 part，watermark 与 seen 状态不变化。
- 一个 session 多条新增 assistant 只查一次标题。
- 空 `session.title`、首 part=text、首 part 非 text、part 缺失四种结果与优化前完全相同。
- watermark 同值多 message、时间戳回跳、seen 超上限、全量重建保持一致。
- 对同一 Fixture 的 `usage_entries`、`conversations`、`opencode_state` 做语义快照比较。

### 阶段 3：缓存标题索引，保留扫描完整性

#### 推荐设计

为进程内 `TitleIndex` 增加只读缓存。第一版使用不会漏掉任意位置改写的内容身份：

```text
IndexIdentity = size + mtime + full-content SHA-256
```

- size/mtime 未变时仍读取文件并计算完整内容指纹；指纹未变才复用解析后的 `HashMap`。
- size/mtime 或完整指纹变化时解析本次已读字节，并原子替换内存缓存。
- 读取或解析失败仍返回空映射／保留现有扫描降级语义，不把标题失败升级为全局失败。
- 缓存只在内存，不新增持久化文件或 schema。

这一步主要减少无变化轮次的 JSON 解析和 `HashMap` 重建，不承诺减少完整文件读取。只有后续
能证明某个平台的文件 change token 对保留时间戳、同尺寸和尾部改写都可靠时，才允许增加更快的
metadata 快速路径；不支持的平台继续完整 hash。短前缀不能证明索引文件整体未变，不能作为
标题缓存的唯一身份。

#### 不在本阶段做

不直接取消所有 JSONL 的 prefix 检查，不改 5 分钟周期，不用文件监听替代全量发现。先测量
目录枚举和 prefix 在完成阶段 1～3 后是否仍是主热点。

### 阶段 4：隐藏窗口不做不可见工作

#### 4.1 主窗口 Dashboard 延迟加载

推荐由 Rust 平台入口在主窗口真正显示时发送一个已有窗口可消费的可见/导航信号，或由前端
可靠读取 `getCurrentWindow().isVisible()` 并监听后续 focus。`MainView` 只有在首次真正可见时
调用 `loadDashboard`；之后沿用 Pinia 缓存和现有 request generation 防旧响应覆盖。

必须覆盖：

- 系统区域“打开 CC Trace”、二次启动、设置入口、快捷键和窗口重新显示。
- 首次打开必须加载，不能依赖用户再切一次范围。
- 主窗口隐藏后自动扫描完成，重新显示时要判断 `finishedAt`／数据版本并刷新一次，不能长期显示
  隐藏前旧汇总。
- 设置页返回用量、Conversations/Timeline 切换和全局数据源筛选不变。

#### 4.2 Router 路由级懒加载

把静态页面 import 改成路由级动态 import，让 compact/onboarding WebView 不解析主窗口图表、
日期选择器和对话页代码。公共 shell、i18n、Pinia 与基础样式仍可共享。

验收必须检查三个窗口首次打开时无白屏、无 chunk 加载错误；离线桌面包的 chunk 全部来自本地
`dist`，不得引入网络依赖。

#### 4.3 秒级时钟按需启停

把 `useTimeText` 拆成分钟级通用能力和最近刷新专用秒级能力：

- `past`、`countdown`、`reset` 只订阅分钟 ticker。
- 只有 Overall Signal 的 `refreshed` 在 `0 <= elapsed < 60s` 且窗口可见时启动 1 秒 ticker。
- 到 60 秒边界立即停止秒级 ticker，切回分钟级。
- 窗口隐藏／失焦时停止；再次显示立即用系统时间校准，需要时恢复剩余的秒级窗口。
- 系统睡眠恢复后立即校准，不能累积 interval 漂移。

功能结果仍需显示 `刚刚已刷新`、`32s 前已刷新`、`1m 前已刷新`；只改变无人在看的定时器生命周期。

### 阶段 5：低风险网络与交互优化

#### 5.1 Statuspage 并发

使用 `tokio::join!` 同时发起 OpenAI 与 Anthropic 请求。两边结果仍分别更新；任何一边失败保留
自己的旧值。仍只在两个结果都返回后发送一次完整 `service-status://updated`。

不改：共享 HTTP Client、15 秒单请求超时、5 分钟周期、手动刷新附带拉取、开关只控制绘制。

#### 5.2 Conversations 项目选项去重载

项目选项只在会影响其结果的条件变化时查询：时间范围、可见服务、全局数据源或扫描数据版本。
搜索文字、Recent/Tokens/Cost 排序、分页与当前项目选择只重载列表，不重复计算项目集合。

必须确认项目列表的现行预期：当前后端 SQL 本来就不应用 search/sort/project，因此减少这些触发
不会改变返回内容。

#### 5.3 Dashboard 查询合并：条件式候选

只有 B8 和 `EXPLAIN QUERY PLAN` 证明 8～10 次聚合是明显热点时，才考虑新增批量查询用例：

- 优先在一个 `spawn_blocking` 任务中复用同一只读连接和一致快照。
- 返回字段继续复用现有 `UsageSummary`，不复制第二套统计算法。
- Rust 与 TypeScript contract 同步；旧 command 可保留给紧凑面板和定向查询。
- 合并前后每个 group、row、total、费用 fingerprint 必须逐字段一致。

如果收益不足，不新增 `usage_get_dashboard`，保留当前简单契约。

### 阶段 6：目录发现与 prefix 的条件式优化

这是风险最高的一项，必须在阶段 1～5 完成后的新基线上重新判断。

#### 可接受方向

1. 文件监听只作为“有变化”的加速提示；监听丢事件后仍有确定性的完整巡检。
2. 使用跨平台可证明稳定的文件 identity/change token 作为快速路径；不支持的平台继续当前 prefix。
3. 对目录结构做进程内缓存，但新目录、新文件、归档移动和权限恢复必须能被下一次 5 分钟扫描
   发现。
4. 将 prefix 校验和 metadata 批量化、减少重复 open/stat，但保持每轮覆盖能力。

#### 不可接受方向

- 只扫描最近 N 天或最近 N 个文件。
- 只依赖根目录 mtime；嵌套目录变化不保证反映到根目录。
- 只依赖文件监听且没有丢事件兜底。
- 仅凭 size/mtime 相同就永久跳过 prefix，导致保留时间戳的覆盖无法发现。
- 为降 CPU 减少扫描数据源、取消 archived、跳过 Pi/OpenCode 或缩短完整行上限。

如果无法在 R 数据集和双平台实机上证明完整等价，本阶段不实施。

## 8. 功能等价验收矩阵

### 8.1 数据结果

优化前后使用同一脱敏输入，比较以下语义快照：

| 对象 | 必须一致 |
|---|---|
| `usage_entries` | source、dedup、conversation、model、speed、geo、时间、六维 Token、费用、Fast 派生、fingerprint |
| `conversations` | source、title、project、sidechain、first/last、source_id、branch |
| `scan_files` | 每文件 mtime、size、offset、prefix、cursor；允许仅实现内部缓存不同 |
| `opencode_state` | watermark 与最近 20,000 seen IDs 的内容和顺序 |
| `quota_events` | 相同额度变化序列；不得重复或漏记 |
| summaries | day/source/model/speed 每行和 totals 完全一致 |
| conversations API | total、稳定排序、分页、项目选项、详情拆分一致 |

数据库自增 `id`、临时文件名和内部执行时刻可不逐字节一致，但业务可观察结果必须一致。

### 8.2 扫描与恢复

- 首次全扫、无变化增量、追加、半行补全、截断、覆盖、同尺寸改写。
- active → archived 移动不重复，Claude 不同目录同 stem 不冲突。
- 取消后 offset 不超前，再次扫描可续。
- 单文件失败不阻断其他来源，状态只包含脱敏计数。
- 价格更新不读 JSONL，active/pending 边界不变。
- 损坏库保留文件组并尽力恢复 `quota_events`。
- schema 过高拒绝，迁移失败回滚。

### 8.3 额度、服务状态与缓存

- 两个 Provider 刷新独立，合并、节流、429/网络退避不变。
- 额度成功、单源失败、身份切换、缓存恢复和 reset 保留一致。
- Statuspage 一边超时不清空另一边；unknown 仍不显示圆点。
- `quota-cache.json` 原子写入、权限与秘密边界不变。

### 8.4 UI

- 应用启动不打开主窗口时不执行 Dashboard 重查询。
- 第一次打开主窗口能立即进入正确路由并开始加载，完成后与当前页面一致。
- compact/onboarding/main 的首次打开和再次打开均无白屏、无 chunk 错误。
- 最近刷新 1 分钟内秒级显示，之后分钟级；隐藏再显示立即校准。
- 扫描 loading、部分失败、未定价、全关空态、长文本、中英文、键盘与 reduced motion 不变。

## 9. 性能与功耗验收门禁

功能等价通过后才看性能。每个阶段独立比较同一机器、同一 release 构建、同一数据集、相同冷/热
缓存条件，至少重复 5 次并记录中位数与离散程度。

### 9.1 硬门禁

- 业务结果差异：`0`。
- 新增秘密、路径或原文日志：`0`。
- 后台网络请求次数不得增加。
- 空闲 CPU time、wakeups、磁盘读写任一项不得出现超过测量噪声的持续回退。
- 主窗口/紧凑面板用户可见延迟不得明显变差。
- macOS 通过不能写成 Windows 已通过；Windows 未测则明确保留未验证。

### 9.2 合并收益门槛

在目标场景中至少满足一项，且其他关键指标无实质回退：

- CPU time 明确下降；或
- 磁盘读取／写入明确下降；或
- wakeups 明确下降；或
- P95 扫描／查询耗时明确下降。

建议把“相对基线至少改善 20%”作为值得保留复杂度的目标，不把它写成已实现承诺。若改善小于
噪声或仅在不现实的超大 Fixture 中出现，应撤回该优化或降低优先级。

### 9.3 预期观察，不是完成声明

| 阶段 | 预期主要改善 |
|---|---|
| SQLite 检查收敛 | 全量扫描与频繁小写事务的数据库读取和耗时 |
| OpenCode 查询收窄 | 无变化／少量新增扫描的 CPU 与上游 DB 读取 |
| 标题索引缓存 | 5 分钟无变化扫描的文件读取和 JSON 解析 |
| 隐藏窗口延迟加载 | 启动 CPU、SQLite 查询数和稳定态 RSS |
| 秒级 ticker 按需 | 隐藏常驻 wakeups 和 WebView 小更新 |
| Statuspage 并发 | 异常网络下单轮活跃时长，不一定降低请求总能量 |
| Dashboard 合并 | 主窗口交互查询耗时与 SQLite 扫描次数 |

## 13. 停止与回退条件

出现任一情况立即停止该阶段，不以继续调参掩盖：

- 任一来源总 Token、费用、对话数或标题规则不一致。
- 截断、覆盖、归档移动或半行续扫出现漏记／重复。
- SQLite 损坏不再被发现、恢复文件组丢失或 `quota_events` 恢复退化。
- 隐藏/显示窗口后数据长期不刷新、导航错误或秒级文案冻结。
- 后台请求数、空闲 wakeups、磁盘写入或稳定态内存反而增加。
- 优化只能通过延长刷新周期、关闭数据源、降低扫描完整性或改变统计口径才能成立。
- 收益小于测量噪声，却显著增加状态、缓存、平台分支或维护成本。

回退优先使用独立提交撤销；不得通过清空用户 `usage.db`、删除外部 JSONL 或重置设置来掩盖问题。

## 14. 最终推荐

建议实施，但按以下策略推进：

```text
先建立基线
  -> 先做 quick_check 与 OpenCode 两个确定热点
  -> 再做标题缓存、隐藏窗口、ticker、Statuspage 等无损优化
  -> 重新采样
  -> 只有证据仍指向目录/prefix 或 Dashboard 时才进入高风险阶段
```

这条路线不改变当前正常需求和功能，主要通过减少重复检查、无新增时的全量查询、不可见窗口工作
和不必要定时器唤醒来优化性能与功耗。任何需要牺牲扫描完整性、数据准确性、状态及时性或恢复
可靠性的方案，都不属于 CC Trace 可接受的性能优化。
