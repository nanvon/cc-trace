# ADR-0011：设置作为主窗口内的二级视图

- 状态：已确认
- 日期：2026-07-25
- 相关文档：[信息架构与核心流程](../信息架构与核心流程.md) 主窗口与设置、[设计方向与状态规范](../设计方向与状态规范.md) 窗口尺寸、[技术架构](../技术架构.md) 窗口与首次启动

## 背景

第 6～8 阶段曾把设置定义为独立、单实例窗口，并按该结构完成原型和第 11 阶段初版实现。实机查看后，产品所有者确认这种分离增加了不必要的窗口切换；首版只有语言、外观、自动刷新、开机启动和版本信息，不足以支撑一个长期独立窗口。

设置与额度总览仍是不同任务，不能把表单直接混入额度内容，也不需要为两者建立侧边栏、Tab 或多层导航。需要改变的是窗口归属，不是设置范围。

## 决策

设置作为主窗口内的二级视图：

- 主窗口默认打开额度总览；“打开 CC Trace”始终回到额度总览。
- 从主窗口、紧凑面板、平台原生菜单或快捷键打开设置时，复用并聚焦同一个主窗口，然后切换到设置视图。
- 设置视图提供明确的“返回额度”入口；返回后恢复到额度总览，并尽量把焦点交还给原触发位置。
- 主窗口不增加常驻侧边栏、Tab 或未来功能占位。额度总览与设置同一时刻只显示一个。
- 切换视图不改变主窗口尺寸、不创建第二个窗口、不使用模态遮罩，也不阻塞后台刷新。
- `⌘W`／`Ctrl+W` 在任一视图都关闭主窗口但不退出应用；`⌘,`／`Ctrl+,` 打开或聚焦设置视图。
- 设置保存、持久化、i18n、状态模型和安全边界保持不变。

实现层保留 `window_open_main` 与 `window_open_settings` 这两个用户意图明确的 command 名称，但二者都操作 `main` 窗口；目标视图通过一条只发给主窗口的导航消息传递。导航目标不是业务状态，不进入 Pinia、设置文件或额度缓存。

## 理由

- 首版设置项少且低频，独立窗口带来的窗口管理成本高于收益。
- 同窗二级视图保持“常用路径在前、偏好设置下一层”的层级，不会把设置表单混进额度判断路径。
- 不使用侧边栏或 Tab，避免把只有两个视图的首版包装成可扩展后台，也不为后续能力预留空导航。
- 同一套窗口语义适用于 macOS 与 Windows；平台差异继续留在 Menu Bar／Tray、快捷键与窗口生命周期，而不是业务视图结构。
- 明确返回路径、稳定窗口尺寸和可恢复焦点符合可预测、可逆和空间一致的桌面交互原则。

## 替代方案

| 方案 | 不采用的原因 |
|---|---|
| 保留独立设置窗口 | 首版设置过少，产生额外窗口、焦点和重新打开成本 |
| 把设置表单直接放在额度总览底部 | 混合高频判断与低频偏好，拉长主阅读路径 |
| 主窗口增加侧边栏或 Tab | 为两个视图引入过重导航，并暗示尚不存在的模块 |
| 使用模态 Sheet／Dialog | 设置不是必须完成后才能继续的短任务，模态会阻塞额度查看 |

## 后果

- Tauri 预创建窗口由四个收敛为三个：`main`、`compact`、`onboarding`。
- `settings` 路由和 `SettingsView` 可以继续复用，但只在 `main` WebviewWindow 内导航。
- 紧凑面板和原生菜单的“设置”入口仍然存在，打开时先关闭紧凑面板，再聚焦主窗口设置视图。
- 原型中“独立设置窗口”的验证结论失效；同窗导航、焦点恢复、重新打开和双平台快捷键需要重新验证。
- 第 11 阶段代码已按本 ADR 收敛为同窗结构；自动化检查与双平台实机验证尚未重跑，不得据此恢复“实机通过”结论。

## 复审条件

- 设置发展为包含多个独立领域、需要长期并排参考额度、或平台规范明确要求独立设置窗口时，重新评估独立窗口。
- 复审不得仅以“未来可能增加设置”为理由提前恢复侧边栏、Tab 或空导航。
