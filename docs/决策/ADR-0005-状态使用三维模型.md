# ADR-0005：展示状态使用三维模型

- 状态：已确认
- 日期：2026-07-25（补写）
- 相关文档：[状态与错误模型](../状态与错误模型.md)、[技术架构](../技术架构.md)

> 决策在第 6 阶段信息架构中已确认，本记录事后补写并补上替代方案与后果。

## 背景

额度监控的状态天然是多维的：应用可能“正在刷新一份已经过期的快照，而失败原因是限流”。如果压成一个互斥枚举，这种组合无法表达，实现只能靠空值和优先级猜测。

Tray 桌面壳预览期为了快速出画面，把状态压成了单一枚举 `loading | live | stale | offline | error`，这恰好暴露了问题：`no_credentials` 与 `rate_limited` 无处安放。

## 决策

每个 Provider 的展示状态由三个独立维度组成，各自独立序列化：

- 活动：`RefreshState`
- 快照新鲜度：`SnapshotFreshness`
- 可用性／失败原因：`ProviderAvailability`

前端不得通过空值、`null` 或空数组推断状态。

## 理由

- “保留旧数据 + 正在刷新 + 上次因限流失败”是常态而非边缘情况，用户需要同时看到这三件事。
- 状态诚实是产品原则之一：旧快照不能因为有数值就显示成功，也不能因为开始刷新就被清空。
- 三维分离后，界面可以独立决定“数值显示什么”“新鲜度标记什么”“解释文案说什么”，不需要为每个组合定义一个新枚举值。
- 失败原因独立后，`no_credentials`、`unsupported`、`rate_limited` 不会被降级成笼统的 `error`。

## 替代方案

| 方案 | 不采用的原因 |
|---|---|
| 单一互斥枚举 | 无法表达组合，值会随场景增加而爆炸 |
| 枚举 + 若干布尔标志 | 布尔组合的合法性无法约束，等于隐式的三维但没有类型保障 |
| 前端按空值推断 | 同一份空数据可能对应加载中、无凭据或错误，推断必然出错 |

## 后果

- 契约与 Pinia 状态更啰嗦，界面需要显式处理组合。
- 桌面壳预览期的互斥枚举成为技术债，已在 [桌面壳验证记录](../桌面壳验证记录.md) 与执行门禁中标记为“接入真实数据前必须替换”。
- 测试需要覆盖组合矩阵而不是单个状态值。

## 复审条件

- 出现第四个必要维度（例如多账号场景下的“账号有效性”），届时应扩展而不是回退到互斥枚举。
