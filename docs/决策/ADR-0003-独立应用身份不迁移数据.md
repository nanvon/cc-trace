# ADR-0003：使用独立应用身份，不迁移 cc-bar 数据

- 状态：已确认
- 日期：2026-07-25（补写）
- 相关文档：[产品定义](../产品定义.md)、[产品范围](../产品范围.md)、[技术架构](../技术架构.md)

> 本记录事后补写，理由依据现有文档重建。

## 背景

Swift 版 cc-bar 已有用户与本机数据：UserDefaults、额度缓存与历史、Usage／Conversation Rollup、Scan State、导入账号、安全存储项、悬浮窗位置、Onboarding 标记。新应用可以选择继承这些数据，或完全独立。

## 决策

CC Trace 使用独立的仓库、应用标识（`com.nanvon.cctrace`）、数据目录、缓存、安全存储 namespace、版本与发布体系。不读取、迁移、覆盖或删除 cc-bar 的任何应用数据。Codex 与 Claude Code 自身的凭据属于外部数据源，可以只读访问。

开发与验收期间两个应用必须能在同一台机器上独立安装并运行。

## 理由

- 新产品重新定义了范围、信息架构与状态模型；旧数据格式对应的是旧语义，迁移会把旧模型带进新应用。
- 迁移代码需要长期维护，而首版还没有稳定的自有格式可迁移到。
- 独立身份让两个应用可以并行运行，便于对照验证。
- 避免任何“升级后旧应用数据被改动”的风险 —— 这类风险不可逆。

## 替代方案

| 方案 | 不采用的原因 |
|---|---|
| 作为 cc-bar 的原地升级 | 用户会预期设置与历史自动保留，实现上要迁移全部旧格式 |
| 只迁移设置，不迁移缓存 | 仍需读取旧 UserDefaults，且部分设置在新范围内已不存在 |
| 读取旧缓存作为首屏数据 | 旧缓存语义与新状态模型不一致，会产生无法解释的状态 |

## 后果

- 用户从 cc-bar 切换到 CC Trace 需要重新设置一次偏好。
- 首版必须验证“新旧应用并行运行互不影响”，并在发布说明中明确不是无损升级。
- 旧 cc-bar 的维护或归档计划留到 CC Trace 发布之后再决定。

## 复审条件

- CC Trace 自身跨版本升级时需要迁移入口，但那属于 CC Trace 自有格式，不改变本决策。
