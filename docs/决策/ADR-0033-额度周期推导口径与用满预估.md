# ADR-0033：额度周期的推导口径与用满预估

- 状态：已确认
- 日期：2026-10-01
- 相关文档：[ADR-0018](ADR-0018-用量数据用SQLite与JSON分域.md)、[ADR-0031](ADR-0031-功能基准改为cc-bar-v1.1.1.md)、[ADR-0032](ADR-0032-额度主体与多账号.md)、[额度领域模型](../额度领域模型.md)、[数据存储与用量索引](../数据存储与用量索引.md)

## 背景

cc-bar v1.1.1 的额度页要回答四个问题：这个周期的额度用了多少（官方口径）、本地花了多少（token 与费用）、照这个速度会用满吗（用满预估）、周期内有没有额外获得额度（额外重置）。它把周期与额度片段持久化在 `quota-cycle-history.json`，并为此写了一整套修复机制：

- `resetsAt` 的秒级抖动（实测 1～3 秒）不能当成新周期，漂移超过 30 分钟才算滚动；
- 跨重启累积的漂移会把周期起点留在旧位置，只能事后按「重置时刻 − 窗口长度」回写；
- 周期可能被记录成多个碎片，需要按最小分片时长与重叠去重合并。

本仓库已经有 `quota_events`：每次采样都会记下每个窗口的剩余值与当时的 `resetsAt`。也就是说，周期与片段所需的全部输入都在，只是没被推导成周期。

## 决策

### 1. 周期与额度片段从事件**现算**，不落盘

`usage::cycle::derive_cycles()` 是纯函数：输入是同一序列
（`provider` × `identity_key` × `window_kind` × `window_id`）按时间升序的采样，
输出是周期与额度片段。查询时现算，不入库。

随之删除 v7 建的三张周期表（`quota_cycles` / `quota_allowance_segments` /
`quota_account_segments`）：它们已无写入方，留着只会变成第二个事实源。

### 2. 边界规则（逐条对齐 cc-bar）

| 情形 | 处理 |
|---|---|
| 采样没有 `resets_at` | 只更新读数；**不开新周期**（那样得到的边界是猜的） |
| `resets_at` 变化 ≤ 60 秒 | 同一次重置的抖动，不建新周期 |
| `resets_at` 变化 ≤ 30 分钟 | 同周期内的漂移，保留既有边界 |
| `resets_at` 变化 > 30 分钟 | 真实滚动：关闭当前周期，按新重置时刻开新周期 |
| 周期内已用回落 ≥ 10 个点 | **额外重置**：开新额度片段，不是新周期 |
| 已用 ≤ 2% 且回落 ≥ 3 个点 | 同上（接近零用量时的小幅回落也是额外重置） |
| 窗口长度未知（Cursor 计费周期桶） | 周期起点取**首次观察时刻**，不按常量猜一个月 |

周期起点 = `resets_at − 窗口长度`；因此 `quota_events` 必须记下 `window_seconds`
（schema v10 新增该列）：窗口长度随服务与套餐变化，不能只按窗口类型取常量。

周期标识 = `provider|identity|window|重置时刻`，纯函数推导下必须稳定，否则同一周期
在两次查询之间会得到两个 id，前端的选中态与对照都会失效。

### 3. 用满预估

- 只用**当前额度片段**的本地用量除以官方已用比例（当前片段观察值 = `latest − baseline`）；
- 整周期预估 = 预估整段量 + 此前片段的实际用量；
- 可信度按官方已用比例分档：≥ 80% 可靠、30–80% 可参考、10–30% 粗略、< 10% 不给数字；
- 官方已用比例为 0 或当前片段没有本地用量时**不预估**：除零与零分子外推出来的数没有意义。

## 理由

- **一致性来自推导，不来自维护**。持久化的周期是一个要和采样同步的状态机，cc-bar 为此写了抖动容差、超长修复、碎片合并三套机制；这些都是「状态与事实不一致」的补丁。现算把这类问题从根上消掉：同一份事件永远给出同一组周期。
- **边界由服务端给，不由我们推**。周期的权威信息是 `resets_at`，我们只是把它记下来。因此「只看查询范围内的采样」也能得到正确边界——不需要为了「完整历史」把全部事件读出来。
- **与仓库既有划分一致**：`usage.db` 存事实（请求级条目、额度事件），派生结果（统计、周期、费用）按需重算，见 [ADR-0018](ADR-0018-用量数据用SQLite与JSON分域.md)。

## 替代方案

1. **照搬 cc-bar 的持久化周期 + 修复机制**。被否决：那套机制存在的理由是它的存储形态（JSON 快照 + 跨重启累积），本仓库的输入是可重放的事件表，不需要为不存在的问题写补丁。
2. **在采样时就把周期写进表**。被否决：写路径要知道「上一份采样」的上下文，扫描与刷新会互相覆盖；读路径现算没有这个耦合。
3. **只显示官方已用比例，不做用满预估**。被否决：用满预估是 cc-bar v1.1.1 的用户可见能力（[ADR-0031](ADR-0031-功能基准改为cc-bar-v1.1.1.md) 第 2 节）。

## 后果

- `quota_events` 增加 `window_seconds`，`usage_get_quota_cycles` 命令返回周期与预估；
- 周期查询默认回看 30 天；因为边界来自 `resets_at`，回看范围内的第一个周期也是准确的；
- 额度页（原时间线视图）上半部分是周期卡、下半部分是历史读数，两者读同一份事件；
- 没有本地用量的服务（Antigravity／Cursor／Command Code）周期卡只显示官方口径与重置时间，用量区显示「无本地用量」。

## 复审条件

- 服务端改成不返回 `resetsAt`（那会让周期边界无处可得，只能退回「按窗口长度猜」）。
- 出现周期级的历史修需求（例如需要保留「当时看到的周期」而不是「按现在的事件重算」的周期）。
