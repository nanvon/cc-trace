# ADR-0018：用量与历史数据改用 SQLite，与 JSON 小状态分域

- 状态：**已提议**（转「已确认」的条件见文末）
- 日期：2026-07-28
- 相关文档：[技术架构](../技术架构.md) §数据与恢复、[数据存储与用量索引](../数据存储与用量索引.md)、[产品范围](../产品范围.md)、[日志与诊断](../日志与诊断.md)
- 前置依赖：产品所有者已表明目标是「重新实现 cc-bar 全部功能」，本地用量、Conversations、Timeline、Pricing 因此从「后续版本评估」上移。该范围调整本身尚未落进 [产品范围](../产品范围.md)，本 ADR 在它确认后才生效。

## 背景

[技术架构](../技术架构.md) §数据与恢复现在写着「首版不创建 Usage、Conversation、Pricing 或 Timeline 数据文件」，全部持久化只有三项：`settings.json`、`quota-cache.json`、`logs/`。在那个范围下 JSON 是正确选择，本 ADR 不推翻它。

产品目标扩大到复刻 cc-bar 全部功能后，新增了一类此前不存在的数据：**GB 级外部日志的派生索引**。这类数据的体量与访问模式和前三项没有可比性。

### 实测体量（2026-07-28，产品所有者本机 macOS）

| 对象 | 实测值 |
|---|---|
| `~/.codex/sessions` | 1.0 GB |
| `~/.claude/projects` | 253 MB |
| JSONL 文件数 | 1769 |
| 旧版 `conversation-rollup.json` | 1.9 MB |
| 旧版 `usage-rollup.json` | 87 KB |
| 旧版 `quota-history-today.json` | 36 KB（**只含当天**） |

### 旧版纯 JSON 方案的实际代价

cc-bar 用 9 个 JSON 文件实现了 Conversations 列表／搜索／排序／分页／详情、每日与按模型统计、Timeline。所以「纯 JSON 做不到」是错的。但它为此付出的代价有记录可查（证据见 [cc-bar-reference/06](../cc-bar-reference/06-状态持久化调度与错误恢复.md)、[05](../cc-bar-reference/05-本地用量对话与计价口径.md)）：

1. **价格表变更触发全量重扫。** pricing fingerprint 绑进 rollup generation，价格一变整套 rollup 失效，必须重扫全部原始日志。按上表体量是分钟级阻塞。价格表更新是常态事件，不是异常。
2. **Timeline 被砍成只有当天。** `quota-history-today.json` 跨天即新建。这不是产品选择，是全量重写模式下累积历史撑不住。旧版事实上不存在跨天的额度曲线。
3. **崩溃即全量重扫。** 「先写 rollup、最后写 scan state，任一失败就 invalidate」——写一半崩溃，下次从 1769 个文件重来。
4. **去重上限 20,000。** `seen IDs` 的硬编码上限是内存与文件体量的妥协，不是业务规则。
5. **增量写入退化为整体重写。** 新增一条消息也要重写整个 1.9 MB 的 `conversation-rollup.json`，且随对话数线性变差。
6. **查询前必须全量反序列化。** 列表的搜索、筛选、排序、分页都在内存里做。

这六条全部源于同一个结构性事实：**JSON 文件的最小写入粒度和最小读取粒度都是整个文件**。数据量小时这是优点（可 `cat`、可整体替换、损坏就删），数据量大时它就是上面六条。

## 决策

**按数据域分开选型，不统一。**

| 数据域 | 存储 | 判据 |
|---|---|---|
| 应用设置 | JSON `settings.json` | 少量标量，整体读写，需人工可读审计 |
| 额度快照缓存 | JSON `quota-cache.json` | < 4 KB，可由 Provider 完全重建，「损坏就删」是优点 |
| 运行日志 | 轮转文本 `logs/` | 追加写；崩溃时需保住已写内容 |
| 价格目录 | JSON `pricing-catalog.json` | 公开小表，整体替换，无查询需求 |
| 逐条用量记录 | **SQLite** | 下表 |
| 对话与详情 | **SQLite** | 下表 |
| 扫描水位与去重 | **SQLite** | 下表 |
| 额度历史（Timeline） | **SQLite** | 下表 |

前四项维持 JSON，**本 ADR 不改动它们的任何现有规则**。物理布局、表结构、索引、事务边界与迁移规则由 [数据存储与用量索引](../数据存储与用量索引.md) 拥有。

### 为什么后四项用 SQLite

按前述六条代价逐条给出第一性收益，不引用「业界常见做法」：

1. **价格变更不再触碰原始日志。** 落库的是**事实**（token 数、时间戳、模型、speed），费用是**派生列**并标记它按哪一版价格算出。价格表更新后只需 `UPDATE` 重算受影响行，1.25 GB 的 JSONL 完全不读。分钟级降到毫秒级。这一条单独就足以支撑本决策。
2. **Timeline 可以真正跨天。** 一天数十行、一年约两万行，按时间范围查询是一次索引扫描。旧版被迫每天丢弃的数据得以保留。
3. **扫描可中断可续。** 一个事务同时提交「本批 entries」与「文件 offset 推进」，两者不可能不同步。崩溃后从断点继续，不需要 invalidate 全量重扫。
4. **去重上限消失。** 唯一索引承担去重，不再需要把 seen IDs 装进内存和文件。
5. **行级增量写入。** UPSERT 替代整体重写，写入量与新增数据成正比而非与总量成正比。
6. **查询不必全量入内存。** 搜索、筛选、排序、分页交给索引和 `LIMIT`。

### 明确不做的事

- **不使用 `tauri-plugin-sql`。** 它把 SQL 执行能力暴露到前端，与 [技术架构](../技术架构.md) §分层与职责「前端只接收脱敏 DTO、不获得通用 fs／http 能力」正面冲突。改用 `rusqlite`（`bundled`）留在 Rust 层，前端一律走既有 command 边界。
- **不把 `settings.json`、`quota-cache.json`、`logs/` 迁入数据库。** 它们进库是净亏：额度缓存「损坏就删」的恢复策略会变成 `integrity_check` + 重建；日志进库会在崩溃时与数据库一起丢失，而需要日志的时刻恰恰是崩溃时刻。
- **不提前抽存储抽象层。** 新增 `src-tauri/src/storage/usage_db.rs`，不改动 `settings_store.rs` 与 `quota_cache.rs`。为想象中的第二种后端付抽象成本没有依据。
- **不读取、不迁移旧 cc-bar 的任何数据文件**，维持 [ADR-0003](ADR-0003-独立应用身份不迁移数据.md)。

## 代价与风险

诚实记录，不粉饰：

- **构建成本上升。** `rusqlite` 的 `bundled` feature 会编译 C 代码（SQLite amalgamation），macOS 双架构与 Windows 三个 Release 产物的构建时间都会增加，Windows 侧走 MSVC 工具链需实测。
- **引入时机因此有约束。** [工程与发布](../工程与发布.md) 的 GitHub 打包链路截至本 ADR 仍**从未实跑**。要求：**先推一个 tag 让打包链路实跑通过，再引入本依赖**，避免同时引入两个未验证变量导致故障归因困难。
- **数据库文件不可 `cat`。** 排查与脱敏审计需要工具。缓解：库内**不得存放任何秘密**（见 [数据存储与用量索引](../数据存储与用量索引.md) §安全边界），审计对象因此仍是「有没有出现不该有的列」，可由 schema 断言覆盖。
- **多出 `-wal`、`-shm` 附属文件**，备份与删除需按整组处理。
- **`quota_events` 不可重建。** 它是观察时点的记录，与其余三张派生表性质不同：派生表迁移失败可以删库重扫，`quota_events` 删了就永久丢失。迁移规则必须区别对待，见规范文档 §迁移。

## 替代方案

| 方案 | 否决理由 |
|---|---|
| 全部维持 JSON（照抄 cc-bar） | 已在「背景」逐条列出六项代价；其中价格变更全量重扫与 Timeline 只能存当天是功能性缺陷，不只是性能问题 |
| 全部迁入 SQLite | 额度缓存丧失「损坏就删」的简单恢复；日志丧失崩溃时的可保存性；为 < 5 KB 的设置引入迁移体系 |
| JSON + 分片／NDJSON 追加 | 能解决 Timeline 累积与增量写入，但不解决价格重算（仍需重扫）与查询前全量反序列化。收益不足以抵掉自建索引与压实逻辑的复杂度 |
| 嵌入式 KV（sled／redb） | 无 SQL 与二级索引，Conversations 的多维筛选排序要自建索引层。对比 SQLite 无净收益 |
| `tauri-plugin-sql` | 破坏前后端分层，见「明确不做的事」 |

## 转为「已确认」的条件

1. [产品范围](../产品范围.md) 完成四档重排，本地用量、Conversations、Timeline、Pricing 正式进入首版必须。
2. 产品所有者对 cc-bar 五项「明确不做」功能（Antigravity、Codex 账号导入、Reset Credits、Statuspage、桌面 HUD）给出结论——其中**账号导入影响 `quota_events` 是否需要账号维度**，见规范文档中标注为「待确认」的字段。
3. GitHub 打包链路完成一次实跑。

三条未全部满足前，本 ADR 不得被当作已生效结论引用，也不得据此开始建库。
