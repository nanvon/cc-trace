# ADR-0023：HeroUI 修复方向定稿（canvas／阴影／大读数／ok 档色）

- 状态：已确认
- 日期：2026-08-08
- 相关文档：[ADR-0012](ADR-0012-视觉方向改为HeroUI风格.md)、[ADR-0017](ADR-0017-系统区域显示额度数字与余量分档.md)、[视觉修复方向评审](../视觉修复方向评审.md)、[设计方向与状态规范](../设计方向与状态规范.md)、`src/styles/tokens.css`、[ADR-0024](ADR-0024-主窗口分组侧边栏导航.md)
- 对照的评审稿：[`prototypes/visual-refresh/`](../../prototypes/visual-refresh/index.html)（仓库内、离线可用，样式真值仍以本 ADR 之后的 `tokens.css` 与[设计方向与状态规范](../设计方向与状态规范.md)为准）

## 背景

[ADR-0012](ADR-0012-视觉方向改为HeroUI风格.md) 确认的 HeroUI 方向落地到实机后，产品所有者发现四类观感问题（2026-08-02 评审稿 `visual-refresh` 确诊，见[视觉修复方向评审](../视觉修复方向评审.md)）：

1. ok 档进度条是 Ink 黑——健康态反而是全面板视觉重量最大的元素，风险层级倒挂。
2. 大读数字号 44px 失衡——数字被过度强调，缺中间层级。
3. 层级不显——canvas `#FAFAFA` 与白卡几乎同色、阴影档位太弱，实机上卡片"浮不起来"，HeroUI 最核心的阴影驱动层级丢失。
4. 排版细节碎——状态点孤悬、花费行 label／value 不对齐、次级窗口像另一套组件。

评审稿针对这四类问题给出修复取值。2026-08-08 产品所有者确认按评审稿**完整还原**，本 ADR 把 🚩 取值从"待确认"转为正式结论。

## 决策

以下取值推翻 [ADR-0012](ADR-0012-视觉方向改为HeroUI风格.md) 决策·颜色／层级与 [ADR-0017](ADR-0017-系统区域显示额度数字与余量分档.md) 的余量四档色表中 `> 50` 档的对应结论：

### 1. 层级改为「色差 + 阴影」共同表达

| 取值 | 原值（ADR-0012） | 新值 |
|---|---|---|
| 浅色 Canvas | `#FAFAFA` | `#F4F4F5` |
| 暗色背景 | `#000000` | `#0E0E11` |
| 暗色表面 | `#18181B` | `#1C1C1F` |
| `--shadow-lane` | 原值 | 加档至静止时肉眼可见（浅色 `0 1px 2px rgb(16 16 20 / 5%), 0 6px 20px -8px rgb(16 16 20 / 10%)`；深色 `0 1px 2px rgb(0 0 0 / 40%), 0 6px 20px -8px rgb(0 0 0 / 35%)`） |

ADR-0012「背景与卡片表面色值刻意非常接近，层级主要靠阴影而不是色差表达」的原则正式修正为：**层级由阴影与色差共同表达**。纯靠阴影在实机（尤其是深色与低对比度环境）上层级不足，因此同时加深 canvas 并加档阴影。浅色下"阴影 + 发丝描边"，深色下"阴影 + 低透明白 ring"的既有兜底模式不变。

### 2. 大读数 44px → 26px

主额度大读数从 `44px` 压制到 `26px`（`%` 号 `15px`，为读数的一半字号并退到 75% 不透明度），专项读数 `15px`。补回「标题 15px → 主读数 26px → 专项读数 15px → 次文字 11px」的中间层级，「strong but not theatrical」由此获得具体标尺。

### 3. ok 档进度条改 success 绿

余量四档中 `> 50` 档的读数与进度条填充从 `--text-primary` 改为 `--status-success`。四档色阶成为完整的 绿 → 黄 → 橙 → 红；stale 降级灰从此与健康态不再撞色。

**ok 绿与成功反馈绿的分工**：两者颜色相同（同一 `--status-success`），但语义与出现位置不同，不冲突：

| 表达 | 语义 | 位置 |
|---|---|---|
| ok 档绿 | 剩余比例充足（余量分档，`quotaTone.ts`） | 进度条填充、百分比读数 |
| 成功反馈绿 | 数据最新／刚完成刷新（状态基调，`status.ts`） | 状态点、状态词 |

刷新完成后状态点的绿与进度条的绿可能同时出现，二者都是「当前数据新鲜且充足」的自然表达；当余量分档降档（warning/low/danger）时进度条转色而状态点仍可保持绿——此时"额度紧张但数据新鲜"两件事各自说清。stale 时整体降级为中性／琥珀，两个维度的绿都不出现。

[设计方向与状态规范](../设计方向与状态规范.md) 第 3.3 节的「`live` 默认使用中性色，仅在刚完成刷新等明确成功反馈中短暂使用绿色」相应改写：live 的**状态表达**默认中性，但**余量分档**的 ok 档使用 success 绿——两者是独立的两个着色维度，互不排除。

### 4. 排版细节统一（同一份评审稿第 1、2 节）

- 状态点并入「刚刚已刷新」新鲜度副标题，头部右侧变为纯动作区。
- 花费行 label–value 成对内联，不再吊孤立灰字。
- 次级窗口（ALL 行）同族样式：同款读数行、`4px` 细条、虚线分隔。
- 图标统一 `16` viewBox / `stroke-width 1.5`。
- 主窗口与 popover 共用同一套卡片语言：`14px` 圆角、边框、加档 lane 阴影（见 [ADR-0024](ADR-0024-主窗口分组侧边栏导航.md)）。

## 理由

- 评审稿是基于实机截图的真实数据确诊的问题，不是猜测；四类问题在浅色、深色下均有复现。
- ok 档必须是绿：ok 用黑造成风险层级倒挂；用灰则与 stale 降级灰撞色，「新鲜且健康」与「数据过期」将无法区分（评审稿第 4 节论证）。
- 色差 + 阴影共同分层是实机验证的结论，纯阴影方案已被证伪，不是局部换色值。

## 替代方案

| 方案 | 不采用的原因 |
|---|---|
| 只改色值，阴影不动 | 实机证明层级仍不显，阴影是 HeroUI 层级的主要载体 |
| ok 档用安静灰 | 灰已被 stale 降级占用，健康态与过期态无法区分 |
| 大读数保持 44px | 数字压倒一切，缺中间层级，产品所有者明确不满意 |

## 后果

- `src/styles/tokens.css` 浅色／深色全部取值已按本 ADR 落地（评审稿 🚩 取值），不再需要改动。
- `docs/设计方向与状态规范.md` 第 3.1、3.2、3.3、3.4 节取值与说明同步改写，第 7.2 节余量分档表 `> 50` 档改为 success 绿。
- `DESIGN.md` 同步改写。
- [视觉修复方向评审](../视觉修复方向评审.md) 的定稿门槛第 1～2 步由本 ADR 与本次文档同步完成；第 4 步实机复核结果待平台验证后写回该文档。
- popover（第 1 节形态）已按本 ADR 实现；主窗口（第 2～3 节）的实现见 [ADR-0024](ADR-0024-主窗口分组侧边栏导航.md)。

## 复审条件

- 若实机验证发现浅色下 `#F4F4F5` 与白卡仍靠阴影不足、或深色下 `#0E0E11`／`#1C1C1F` 对比不充分，调整 canvas 与 lane 阴影档位，不需整体推翻。
- 若 ok 档常驻绿色造成「剩余充足」与「刚刚刷新成功」在快速扫视时混淆（评审稿标注的最大冲突面），重新评估第 3.3 节分工，优先考虑状态点换形（不换色），而不是退回黑条。
