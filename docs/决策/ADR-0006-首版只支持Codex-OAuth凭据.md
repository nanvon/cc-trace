# ADR-0006：首版只支持 Codex OAuth 凭据

- 状态：已确认
- 日期：2026-07-25
- 相关文档：[额度领域模型](../额度领域模型.md) 第 5 节、[产品范围](../产品范围.md)

## 背景

Codex 的本机凭据文件可能保存 OAuth 凭据，也可能保存 Personal Access Token。旧版对两者都做了支持：PAT 是不透明字符串，没有 JWT、没有 refresh，账号身份要靠一次 usage 响应回填（证据等级“代码已确认”，见 [04-账号凭据Provider与额度协议](../cc-bar-reference/04-账号凭据Provider与额度协议.md)）。

## 决策

首版只使用自动发现的 Codex OAuth 凭据。凭据文件存在但只含 PAT 时，该 Provider 报 `unsupported`，并说明首版支持范围与用户可以做什么。

## 理由

- PAT 需要一条独立的身份获取路径（先请求、再回填身份），会让首版的凭据发现出现两套语义。
- 首版明确不做账号导入、编辑与切换，PAT 的典型使用场景（粘贴导入、多账号）本就在范围之外。
- `unsupported` 状态本来就是首版必须实现的状态之一，PAT 给了它一个真实用例，不需要新增分支。

## 替代方案

| 方案 | 不采用的原因 |
|---|---|
| 首版同时支持 PAT | 增加身份回填路径与额外请求，首版收益低 |
| 发现 PAT 时报 `no_credentials` | 不诚实：凭据存在，只是不受支持，用户会去做无用的重新登录 |
| 发现 PAT 时静默忽略该 Provider | 违反状态诚实原则，Provider 会无声消失 |

## 后果

- 使用 PAT 的 Codex 用户在首版看不到额度，只能看到明确的“不支持”说明。
- `unsupported` 的文案必须说清支持范围，不能只说“出错了”。

## 复审条件

- Provider 最小闭环验证发现 PAT 在实际用户中占比可观。
- 后续版本引入账号导入或多账号管理时，PAT 应与之一并设计。
