# ADR-0017：系统区域显示额度数字，紧凑面板改图标操作，新增余量四档色

- 状态：已确认
- 日期：2026-07-27
- 修订：2026-07-28，主额度从固定 5 小时窗口改为 Provider 输出第一项；菜单栏徽标加入光学补偿
- 相关文档：[信息架构与核心流程](../信息架构与核心流程.md)、[设计方向与状态规范](../设计方向与状态规范.md)、[状态与错误模型](../状态与错误模型.md)、`src/styles/tokens.css`、`src-tauri/src/platform/tray.rs`
- 对照的探索稿：Artifact「CC Trace · HeroUI 方向」<https://claude.ai/code/artifact/5aef7024-5acb-4184-889a-24bfabd3a0ed>（外部留档，性质见 [ADR-0012](ADR-0012-视觉方向改为HeroUI风格.md)）

> 本 ADR 在稿子基础上做了三处偏离，稿子里是旧形态：标题改为固定表面名加状态点（第 2b 节）、系统区域新增百分比位图（第 1 节，稿子未覆盖）、`--status-low` 从稿子标注的“待定”改为正式采纳（第 3 节）。照稿子实现前先读这三节。

## 背景

[ADR-0012](ADR-0012-视觉方向改为HeroUI风格.md) 把视觉方向改为 HeroUI 风格，但只替换了 token 取值与组件的形状、阴影、提示条形态，没有改动紧凑面板与主窗口的**布局结构**。产品所有者在实机观感上提出两点：

1. 菜单栏图标只有一个静态品牌符号，无法在不打开面板的情况下知道额度，要求做成 Swift 版 cc-bar 的形态——图标旁并排显示 Codex 与 Claude Code 的主额度剩余百分比。2026-07-28 产品所有者进一步明确：主额度不是固定的 5 小时窗口，而是 Provider 标准化输出的第一项；Codex 当前只有 weekly 时，卡片第一行和菜单栏都必须显示 weekly。
2. 紧凑面板与 HeroUI 探索稿（Artifact `CC Trace · HeroUI 方向`）差距明显：稿子里操作集中在面板头部的图标按钮组，Provider 是带 chip、大百分比读数、虚线分隔子额度行的卡片；实现里操作是底部三个文字按钮，Provider 只有状态词加带标签的进度条，没有百分比读数。

产品所有者要求紧凑面板与主窗口「和 Artifact 一模一样」。

本决策同时处理这两项要求所推翻的三条既有结论。

## 决策

### 1. 系统区域显示两个 Provider 的第一项额度数字

正式撤销 [信息架构与核心流程](../信息架构与核心流程.md) 第 4.3 节的这一条：

- ~~不把彩色百分比、多个 Provider 数字或错误长文案塞进系统区域。~~

改为：系统区域承载两个 Provider 标准化输出的第一项额度剩余百分比，形态与约束如下。

- **macOS**：Rust 侧把「Codex 标识 + 百分比」「Claude Code 标识 + 百分比」合成一张位图，作为托盘图标，并保持 template——由 macOS 按当前菜单栏外观着色，因此**仍然不是彩色百分比**，撤销的只是「多个 Provider 数字」。图标与文字间距 3pt、两段之间 9pt；每段文字按当前内容的真实宽度排布，不为 `100%` 预留固定槽位，因此菜单栏 item 宽度会随数字位数自然变化。Tauri 底层 `tray-icon` 会把任意图片统一设为 18pt 高，因此 CC Trace 直接使用 18pt 画布并按 **2×** 输出 36px；不能先画 cc-bar 的 22pt 透明画布再交给 Tauri，否则整张图会被缩到 18pt，标识与文字都会变小并产生额外重采样。由于 `resvg`／`tiny-skia` 的实际墨量比 cc-bar 的 AppKit／Core Text 渲染更轻，CC Trace 在最终 18pt 画布内使用 **19pt 标识、13.5pt Medium 系统字体**作光学补偿；这是渲染链差异补偿，不改变两段的布局语法。
- **Windows**：System Tray 不支持图标旁并排文字，托盘图标尺寸也不足以承载两组数字。Windows 保留静态品牌图标，把同一份文本放进 tooltip。2026-07-28 产品所有者确认这就是 Windows 的终态：**不在托盘图标上画动态数字位图**，无需悬停即可见的额度由后续版本的桌面悬浮窗承担——它本来就在 [产品范围](../产品范围.md) 的「后续版本评估」里，不为 Windows 单独立项。因此 `tray.rs` 的位图渲染保持 `#[cfg(target_os = "macos")]`，这不是未完成的缺口。
- 无快照或 `windows` 为空时该段显示 `--`；两个 Provider 都没有数据时仍渲染一个标识占位，图标不消失（保留第 4.3 节原有的这条约束）。
- 只显示 `QuotaSnapshot.windows[0]`，与卡片第一行共用 [额度领域模型](../额度领域模型.md) 的主次规则；不按窗口类型或 `isPrimary` 重新选择，也**不新增设置项**。cc-bar 的「主要 / 每周 / 两者」选择器不进入首版，否则会扩大 [产品范围](../产品范围.md) 的「基础设置」。

第 4.3 节其余三条（使用微型品牌标识、必须在浅色深色高对比下可辨识、没有数据时图标不消失）继续有效。

### 2. 紧凑面板操作改为头部图标按钮组

正式撤销 [设计方向与状态规范](../设计方向与状态规范.md) 第 7.5 节的这一条在紧凑面板上的适用：

- ~~主要刷新、查看详情和完成首次启动使用清晰文字，不依赖图标猜测。~~

改为按界面区分：

- **紧凑面板**头部使用图标按钮组（刷新、打开 CC Trace、设置、退出），每个按钮必须有 Tooltip 与可访问名称。面板宽 380px，四个文字按钮会挤压 Provider 卡片的横向空间，且 Artifact 已确认的形态是图标组。
- **主窗口**和**首次启动**的主要动作继续使用清晰文字（「刷新」「设置」「返回额度」），不改。

[信息架构与核心流程](../信息架构与核心流程.md) 第 4.2 节「紧凑面板内必须始终能找到设置和退出」的要求不受影响——两者都在头部按钮组里。

### 2b. 总体状态不再是一句话标题

两个表面的标题都改成稳定的表面名（紧凑面板「用量」、主窗口「额度总览」），不再把总体状态写成整句。产品所有者 2026-07-27 实机查看后明确要求去掉「两个 Provider 都是最新数据」这类文案：它长、啰嗦，而且在最不需要注意的状态下占据最显眼的位置。

总体状态改由标题右侧的状态点承担，四态对应「数据是最新的 / 部分数据已过期 / 有需要处理的问题 / 尚未连接」。状态点带 `role="img"` 与可访问名称，因此颜色不是唯一载体，[设计方向与状态规范](../设计方向与状态规范.md) 第 3.3 节的「色彩不能单独承担状态」仍然成立。需要处理的事仍然在对应 Provider 的提示条里说清楚，屏幕阅读器的 `aria-live` 播报也保持原样。

`overall.allHealthy` 与 `overall.focus` 两个 key 随之删除。

紧凑面板打开时，程序化焦点落在稳定标题「用量」而不是刷新按钮；标题通过 `tabindex="-1"` 承接辅助技术焦点，但不画容易被误解为选中态的蓝色焦点环。用户按 `Tab` 后进入刷新按钮，此时继续使用全局 `:focus-visible`，键盘焦点没有被移除。

### 3. 新增额度余量四档色，与状态基调并存

这是本 ADR 唯一涉及**语义新增**的部分，不是纯视觉调整。

现有 `src/lib/status.ts` 的 `StatusTone`（`neutral` / `warning` / `critical`）由**可用性维度**决定：只要 `availability` 是 `ready` 且 `freshness` 是 `live`，无论剩余 5% 还是 95%，百分比都是中性色。[设计方向与状态规范](../设计方向与状态规范.md) 第 7.2 节原本也是这个口径。

Artifact 引入了第二个维度：颜色由**剩余百分比**决定。两者不能互相替代——「凭据失效」和「只剩 3%」是两件不同的事，必须能同时表达。因此新增独立的余量基调：

| 剩余百分比 | 余量基调 | 浅色 | 深色 |
|---|---|---|---|
| 无数值 | `none` | `--text-secondary` | 同左 |
| `> 50` | `ok` | `--text-primary` | 同左 |
| `20 ≤ pct ≤ 50` | `warning` | `--status-warning` | 同左 |
| `0 < pct < 20` | `low` | `--status-low` `#f3730e` | `#ff8a3d` |
| `= 0` | `danger` | `--status-error` | 同左 |

- 余量基调只驱动**百分比读数与进度条填充**的颜色。
- 状态基调继续驱动**状态提示条、状态点与状态词**。
- 快照不新鲜（`rail` 为 `faded`）时余量基调整体降级为中性，避免「旧数据用鲜艳颜色宣称紧张」。
- `--status-low` 不是 HeroUI 官方语义色。HeroUI 官方只有 `primary / success / warning / danger / default`，没有介于 warning 与 danger 之间的档位。Artifact 自己也标注了这一点。本 ADR 正式采纳 `#f3730e` / `#ff8a3d`，结束这个悬空取值。

[状态与错误模型](../状态与错误模型.md) 的三维契约、状态优先级和组合矩阵**不受影响**：余量分档是展示层对同一份 `remainingPercent` 的着色规则，不产生新的状态值，也不进入 Rust 契约。

## 理由

- 菜单栏常驻显示额度是 cc-bar 用户已经建立的使用习惯，也是「常驻额度监控」这个产品定位最直接的兑现方式：不点开任何窗口就能回答「现在紧不紧」。原第 4.3 节的顾虑是「彩色数字污染系统区域」，模板位图方案用单色渲染避开了这个顾虑的实质。
- 卡片第一行和系统区域如果各自按窗口类型选择，会在 Codex 只有 weekly 时出现「卡片有数值、菜单栏是 `--`」的冲突。统一使用 Provider 第一项让两处共享同一业务事实，也适配 Provider 窗口结构变化。
- 图标按钮组的可发现性顾虑由 Tooltip 与可访问名称兜底；紧凑面板的四个操作都是常驻工具类动作（刷新、打开、设置、退出），不是需要文字说明的破坏性或分支动作。
- 余量四档色让「额度快用完」在不读文字的情况下可辨识，这是额度监控工具的核心信息。只用状态基调时，`live` 且剩余 3% 与 `live` 且剩余 93% 视觉完全相同，这是当前实现的真实缺陷。

## 替代方案

| 方案 | 不采用的原因 |
|---|---|
| macOS 用 `tray.set_title()` 显示纯文字 | 零新依赖，但两个数字只能靠顺序区分，没有 Provider 标识；产品所有者明确选择复刻 cc-bar 的图标加数字形态 |
| Windows 把数字画进 16×16 托盘图标 | 两组「标识 + 百分比」在 16px 高度内不可读 |
| 用状态基调兼任余量分档 | 会让「凭据失效」与「额度紧张」共用一套颜色，两件事无法同时表达 |
| 直接改 `StatusTone` 增加 `low` 档 | `StatusTone` 的取值来自可用性维度，混入余量档位会让 `src/lib/status.ts` 同时承担两个语义来源 |
| 保留底部文字按钮，只改视觉 | 产品所有者要求与 Artifact 一致；380px 宽度下四个文字按钮会挤压卡片 |

## 后果

- `src-tauri/src/platform/tray.rs` 从静态图标改为按快照重建；新增位图渲染模块与 Provider 标识资源。渲染依赖 `resvg` / `tiny-skia` / `usvg`，见「新增依赖」。
- 卡片主行与系统区域都直接取 `QuotaSnapshot.windows[0]`；Provider 解析器仅把第一项标记为 `isPrimary`，消费方不再根据类型或该标记重排。
- Provider 标识 SVG 取自 `../cc-bar/Resources/Logos/`（`codex.svg`、`claude.svg`），复制进本仓库自有资源目录。它们只用于在本机界面上标识对应 Provider，不作为 CC Trace 的品牌标识使用。
- `src/styles/tokens.css` 新增 `--status-low`；[设计方向与状态规范](../设计方向与状态规范.md) 第 3.4 节映射表同步新增一行。
- 新增 `src/lib/quotaTone.ts` 承载余量分档，与 `src/lib/status.ts` 并列。两者都是纯函数，各自有单元测试。
- `ProviderLane.vue`、`QuotaProgress.vue`、`StatusExplanation.vue`、`OverallSignal.vue`、`CompactView.vue`、`MainView.vue` 布局改写；i18n 中英文同步新增 key。
- [设计方向与状态规范](../设计方向与状态规范.md) 第 3.4、7.1、7.2、7.4、7.5 节与第 8 节状态矩阵需要同步改写。
- [信息架构与核心流程](../信息架构与核心流程.md) 第 4.3、5 节需要同步改写。
- **Windows 侧的 tooltip 方案代码可写但无法验证**——没有 Windows 主机。与 [ADR-0015](ADR-0015-第12阶段先于桌面壳实机验证启动.md) 的口径一致：不得标记为已通过。
- **macOS 侧的菜单栏位图经过三轮实机反馈**：2026-07-27 产品所有者确认首版图标与文字明显偏小；2026-07-28 进一步定位到不是单纯缺少 2×，而是 Tauri 把 22pt 画布再次缩到 18pt。实现先改为最终 18pt／36px 画布并原子设置 template，同日移除 `100%` 固定文字槽位，恢复 cc-bar 的自然文字宽度；继续与 cc-bar 对照后，产品所有者确认图标和文字仍小半档、细半档，因此加入 19pt 标识与 13.5pt Medium 文字的光学补偿。补偿后的实际观感仍需复看，模板着色、深色菜单栏可辨识度和自然宽度变化仍在 [桌面壳验证记录](../桌面壳验证记录.md) 的走查清单里。
- 字体族和字号是实测结论，不能凭名字猜：2026-07-27 已确认 `SF Pro`、`.SF NS Text`、`.AppleSystemUIFont` 都能解析到系统 UI 字体；2026-07-28 只读查询 AppKit，`NSFont.menuBarFont(ofSize: 0)` 实际为 `.AppleSystemUIFont` 13pt，`monospacedDigitSystemFont` 为 `.SFNS-Regular` 13pt。`SF Pro Text` 不存在会静默回退 Helvetica。`menubar_badge.rs` 用测试守住字体解析和 36px Retina 输出——静默回退不会报错，只会变丑。

### 新增依赖

| Crate | 用途 | 取舍 |
|---|---|---|
| `resvg` | 渲染 Provider 标识 SVG 与百分比文字到位图 | 相比 `tiny-skia` + `ab_glyph` 手工排版，`resvg` 能直接吃现成 SVG 并用系统字体渲染文字，不需要自己做字形排布 |
| `tiny-skia` | `resvg` 的像素后端，输出 RGBA 供 Tauri `Image` 使用 | `resvg` 的传递依赖，显式声明以便直接操作 `Pixmap` |

两者都是纯 Rust，不引入系统图形库，两个平台构建条件一致。

## 复审条件

- 若 macOS 实机发现模板位图在深色菜单栏或高对比模式下不可辨识，先调整标识线宽与字重，不需要退回纯图标方案。
- 若菜单栏位图的重绘频率造成可观测的能耗或闪烁，改为只在百分比取值变化时重建位图，仍不退回静态图标。
- 若取得 Windows 主机后发现 tooltip 无法承载（例如更新不及时或长度受限），走悬浮窗补齐，不回头在 16×16 托盘图标上做动态数字——两者解决的是同一个「无需悬停即可见」的需求，做了托盘位图就是重复投入。macOS 侧决策不受影响。
- 若后续产品所有者要求按窗口切换菜单栏显示内容（cc-bar 的 `menuBarWindow`），那是 [产品范围](../产品范围.md) 的「基础设置」扩项，需要单独决策并替代“第一项即主数据”的当前规则，不在本 ADR 授权范围内。
