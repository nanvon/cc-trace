# 性能基线验证记录

> 状态：阶段 0 基线已采集（2026-08-13）
> 方案：`docs/性能与功耗优化方案.md`
> 平台：macOS 27.0（Apple M1 Pro，arm64）
> 构建：release（`cargo run --release`，`perf-baseline` feature 开启统计计数器）

## 1. 数据集（`examples/usage_dataset.rs` 派生，位于 /tmp/cc-trace-datasets/，不入仓库）

| 数据集 | 组成 | 规模 |
|---|---|---|
| S | `fixtures/usage/` 现有脱敏 Fixture | 3 文件、17 行 |
| M | 机械复制并改写脱敏 ID／时间戳 | 300 文件（codex 135 / claude 135 / pi 30）、每文件 150 行，约 4.5 万行，9.7 MiB |
| L | 同上放大 | 3000 文件、约 45 万行，97 MiB |
| R | 截断、同尺寸改写、归档重复、半行、无效 JSON、超长行（>16 MiB）、OpenCode 首 part 非 text | 9 个异常文件 + 对照 |

M/L 的 OpenCode 数据库（200／300 sessions）由派生工具用 rusqlite 按
`usage/opencode.rs` 测试同构 schema 构造，全脱敏。

## 2. 命令

```text

cargo run --release --example usage_bench --features perf-baseline --
```

## 3. B1 全量重建（每次迭代全新 config 目录）

| 数据集 | 重复 | 总耗时中位数 | 批提交耗时占比 | quick_checks | write_opens | batch_commits | 读取字节 |
|---|---|---|---|---|---|---|---|
| M | 5 | 826 ms（738–990） | ~60%（454–547 ms） | 302 | 303 | 301 | 8.5 MiB |
| L | 3 | 24.4 s（24.0–28.5） | ~82%（19.8–23.2 s） | 3002 | 3003 | 3001 | 84.3 MiB |

- 实测确认：**每批提交（含 OpenCode 提交与 `save_opencode_state`）都重新打开写连接并执行
  `PRAGMA quick_check`**；批次数 = 文件批数 + 1，quick_check 次数 = 批次数 + 1（`initialize`
  后的首次打开无检查，写连接总次数再 +1 来自 `save_opencode_state`）。
- 规模放大：文件数 ×10（M→L）时全量重建耗时 ×30，批提交耗时占比 60% → 82%，
  与「quick_check 为 O(N) 全库扫描、与批次数相乘」的预期一致。
- 每批平均提交耗时约 6.6 ms（L，含 8 MiB 级库的 quick_check）。

## 4. B2 连续无变化扫描

| 数据集 | 每轮耗时 | quick_checks | batch_commits | 读取字节 |
|---|---|---|---|---|
| M（300 文件） | 20 ms（19–23） | 1（仅 initialize） | 0 | 0 |
| L（3000 文件） | 155 ms（153–162） | 1（仅 initialize） | 0 | 0 |

- 无变化扫描不产生批提交，成本集中在目录遍历与每文件 4 KiB 前缀 SHA-256 校验。
- 阶段 1（收敛 quick_check）对日常无变化扫描**无直接收益**；收益集中在全量重建、
  追加大量数据、OpenCode 提交等产生写事务的场景。

## 5. B5 OpenCode（200 sessions × 20 messages + parts，全脱敏）

| 轮次 | 耗时 | batch_commits | quick_checks |
|---|---|---|---|
| 全量重建（新 db） | 55 ms | 1 | 2 |
| 无新增（同 db 重扫） | 15 ms | 0 | 1 |
| 少量新增（1 message + 2 parts） | 35 ms | 1 | 2 |

- 无新增时 `part` 标题查询仍在执行，但当前规模（200 sessions）下仅占 ~15 ms。
- 批提交在 OpenCode 全量重建中占 ~45%（25 ms / 55 ms）。

## 6. R 异常数据集

- B1 一次扫描 39 ms 完成，不崩溃；超长行（>16 MiB）被隔离为失败文件，单文件失败
  不阻断其他来源（completed 8/9），符合「状态只包含脱敏计数」语义。
- R 数据集用于阶段 1／2 的功能等价验收（`docs/性能与功耗优化方案.md` §8.2），
  基线阶段只验证了构造与扫描器容错。

## 7. 未验证与边界

  （文档 B0／B7 场景）。
- Windows 侧全部未验证；本记录全部结论仅适用于 macOS（arm64）。
- 数据集生成只机械复制 Fixture 并改写脱敏 ID／时间戳，未引入真实标题、路径、账号或

## 8. 阶段 1 优化后复测（2026-08-13）

实现：`open_write` 拆为 `initialize`（一次性 quick_check＋迁移＋pragma）与
`open_write_unchecked`（纯打开）；`verify_after_logical_write` 在每次完整扫描、重计价、
重建与额度历史写入的边界执行一次 quick_check；批次不再逐批检查
（`docs/性能与功耗优化方案.md` 阶段 1）。

同一机器、同一数据集、同一 release 构建、相同命令复测：

| 场景 | 优化前 | 优化后 | 变化 |
|---|---|---|---|
| B1 全量重建（M） | 826 ms 中位；quick_checks 302 | 513 ms 中位；**quick_checks 1** | 总耗时 -38% |
| B1 全量重建（L） | 24.4 s 中位；quick_checks 3002 | 6.1 s 中位（4.8–6.8）；**quick_checks 1** | 总耗时 -75% |
| B1 批提交总耗时（M） | 482–547 ms | 254–264 ms | -52% |
| B1 批提交总耗时（L） | 19.8–23.2 s | 2.3–2.8 s | -88% |
| B2 无变化扫描（M） | 20 ms | 18 ms | 无回退 |
| B5 无新增 | 15 ms | 10 ms | 无回退 |
| B5 少量新增 | 35 ms | 11 ms | -69% |

- quick_checks 从「批次数 + 1」收敛为「1（全新库）／2（已有库：initialize + 扫描结束边界）」，
  由 `perf_baseline_scan_checks_once_per_logical_write_not_per_batch` 测试锁定。
- 收益随库体积放大：文件数 ×10（M→L）时优化后总耗时不再随批数线性放大，
  L 级批提交总耗时占比由 82% 降至 ~45%。
- 损坏恢复语义不变：`verify_after_logical_write_recovers_a_database_corrupted_after_
  initialization` 覆盖「运行中损坏 → 受写锁保护的恢复 → 再次验证健康」，损坏文件组保留。
- 全部 244 项 Rust 单测通过（含既有损坏恢复、schema 版本、重建一致性与语义快照测试）。

## 9. 阶段 2 优化后复测（2026-08-13）

实现：OpenCode 标题兜底改为「先收集本轮候选空标题 session，再只对这些 session 分块查询
首 part」；`seen_order` 改用 `VecDeque`（`docs/性能与功耗优化方案.md` 阶段 2）。

| B5 场景（200 sessions × 20 messages） | 阶段 1 后 | 阶段 2 后 |
|---|---|---|
| 全量重建 | 47 ms | 46 ms |
| 无新增（同 db 重扫） | 10 ms | **6 ms**（-40%） |
| 少量新增（1 message + 2 parts） | 11 ms | 9 ms |

- 无新增时 `needs_part_title` 为空，不再发起任何 part 查询；watermark 与 seen 状态不变，
  由 `part_title_fallback_ignores_non_text_first_part_and_keeps_state_on_noop` 测试锁定。
- 功能等价：首 part=text、首 part 非 text、part 缺失、多条新增 assistant 共享一次标题查询、
  无新增去重五类结果与优化前一致（新增定向测试覆盖非 text 与共享标题）。
- 全量 245 项 Rust 单测通过，clippy `-D warnings` 通过。

## 10. 阶段 3（标题索引缓存）决策输入

按方案 §1.2 降级为「先测再决定」：用 B2 数据判断。L 级（3000 文件）无变化扫描每轮
155 ms 中，标题索引只是 2 个 JSONL 文件的完整读取与解析（码级毫秒）；主要成本是目录遍历
与每文件 4 KiB 前缀 SHA-256。缓存只能省 JSON 解析与 HashMap 重建，**收益远小于测量噪声，
不实施**（符合原则 6「无实测收益不引入复杂度」）。

## 11. 阶段 4／5 前端与网络改动（2026-08-13，自动化验证）

### 4.1 主窗口 Dashboard 延迟加载（`MainView.vue`）

- 挂载时先探测 `getCurrentWindow().isVisible()`：不可见（启动预创建隐藏窗口）不加载，
  等待 `navigation://main` 事件（tray 点击、二次启动、设置入口、快捷键等全部主窗口打开
  路径已由 `desktop.rs::show_main` 发送）；纯浏览器预览兜底视为可见。
- 重新显示时比较 `usage.status.finishedAt`：隐藏期间后台扫描已完成则刷新一次，避免长期
  显示隐藏前旧汇总；未变化沿用 Pinia 缓存与 request generation 竞态保护。
- 从设置／Timeline／Conversations 切回用量页是「挂载且可见」，保持原有无条件加载语义，
  数据源筛选等交互不变。
