## 结论

第 8 阶段采用仓库内隔离的 HTML/CSS/JavaScript 原型，验证 CC Trace 的窗口职责、核心流程、双平台等价入口与完整状态表达。

原型位于 [`prototypes/tray-shell/`](../prototypes/tray-shell/README.md)，不属于 `src/` 正式应用，不连接 Provider，不读取凭据，不写入缓存，也不代表 Tauri Tray 已实现。

原型确认采用以下边界：

- macOS 与 Windows 共享业务语义、额度数据和窗口职责。
- macOS 使用顶部 Menu Bar 入口；Windows 使用底部 System Tray 入口。
- 主点击打开紧凑额度面板。
- Windows 右键额外提供原生语义的 Tray 菜单。
- 主窗口与设置均为独立、单实例语义的窗口。
- 首次启动只解释数据边界并报告凭据发现结果，不在应用内登录。
- 首版没有本地用量、Conversations、Timeline、Pricing、其他账号和悬浮窗，因此不为这些能力创建空导航或占位原型。

## 原型控制

原型顶部工具栏只用于评审，不进入正式产品：

| 控制 | 可验证内容 |
|---|---|
| 平台 | macOS Menu Bar、Windows System Tray |
| 状态 | 成功、加载、无凭据、离线旧快照、刷新受限、单 Provider 错误 |
| 外观 | 浅色、深色 |
| 首次启动 | 数据边界、凭据发现结果、进入紧凑面板 |

## 窗口与入口矩阵

| 对象 | macOS | Windows | 共同职责 |
|---|---|---|---|
| 系统入口 | Menu Bar 图标 | System Tray 图标 | 提供随时可达的额度入口 |
| 主点击 | 打开／关闭顶部紧凑面板 | 打开／关闭底部紧凑面板 | 查看当前额度、重置时间和异常 |
| 辅助菜单 | 紧凑面板内提供设置和退出 | 右键 Tray 菜单提供打开、刷新、设置、退出 | 不改变业务语义 |
| 主窗口 | 独立窗口 | 独立窗口 | 展开 Provider 详情并解释数据可信度 |
| 设置 | 独立单实例窗口 | 独立单实例窗口 | 管理刷新、开机启动、语言与外观 |
| 首次启动 | 独立模态流程 | 独立模态流程 | 解释不迁移旧数据、不暴露凭据原文 |

## 状态覆盖

| 状态 | 总览表达 | Provider 表达 | 用户下一步 |
|---|---|---|---|
| `live` | 额度状态正常、刚刚刷新 | 实时额度与重置时间 | 查看详情或等待自动刷新 |
| `loading` | 正在刷新 | 保留上一份有效快照并标记刷新中 | 可继续阅读旧值 |
| `no_credentials` | 尚未发现可用凭据 | 不伪造 `0%`，显示无凭据 | 在对应 CLI 完成登录后刷新 |
| `offline + stale` | 当前离线，显示旧快照 | 标出离线和旧快照 | 网络恢复后刷新 |
| `rate_limited + stale` | 单 Provider 刷新受限 | 保留旧快照并给出可重试时间 | 等待冷却，不影响其他 Provider |
| `error` | 单 Provider 需要处理 | 错误 Provider 无额度；其他 Provider 继续显示实时值 | 检查对应 CLI 登录状态 |

状态不只依赖颜色：标题、状态文案、额度符号和辅助说明共同表达语义。没有可用额度时，进度轨道使用“无可用额度”的可访问性文本，不把未知值读成零。

## 已走通的核心流程

1. 系统图标 → 紧凑额度面板 → 查看详情 → 独立主窗口。
2. 系统图标 → 紧凑额度面板 → 设置 → 独立设置窗口。
3. Windows Tray 右键 → 打开、刷新、设置或退出。
4. 首次启动 → 阅读数据边界与凭据发现结果 → 开始使用 → 紧凑额度面板。
5. 切换状态 → 紧凑面板与主窗口同步显示同一份合成快照。
6. 刷新 → 进入加载状态，同时保留上一份有效数据。
7. `Escape` → 关闭紧凑面板 → 焦点返回系统图标。
8. 点击紧凑面板外部 → 关闭临时面板；打开主窗口或设置时也先关闭临时面板。

## 视觉与可访问性验收

- 使用 `Reset Rail / 重置轨道` 方向：稳定 Provider 轨道、明确额度与重置关系，不使用通用卡片仪表盘。
- 使用正式 CC Trace Symbol，不使用临时字母徽标。
- 支持浅色、深色和窄窗口布局。
- 交互控件具有可见焦点，主要按钮最小高度为 `40px`。
- 表单控件都有可见标签；图标按钮都有可访问名称。
- 主窗口、设置和首次启动使用原生 `dialog` 语义，并由浏览器管理焦点约束。
- 动效服从 `prefers-reduced-motion`。
- 加载区域使用 `aria-busy`；状态切换区域使用 `aria-live`。
- 额度数字使用表格数字，便于刷新前后比较；等宽字体只用于工具元数据和额度数据。
- `kill-ai-slop` 扫描结果为 `0` 项：没有无意义渐变、玻璃拟态、徽标堆叠、泛化营销文案或临时字母 Logo。

## 浏览器验证记录

2026-07-25 使用真实 Chromium 页面完成以下检查：

- 页面和品牌资源均能加载，无业务脚本控制台错误。
- 首次启动打开后焦点进入模态窗口；“开始使用”关闭窗口并展示紧凑面板。
- Windows 平台切换后，主点击打开紧凑面板，右键显示 Tray 菜单。
- 无凭据状态不会暴露或伪造额度值。
- 紧凑面板能打开主窗口和设置窗口，状态语义保持一致。
- `Escape` 关闭紧凑面板后，焦点返回系统图标。
- 设置窗口在 `1280 × 720` 视口下完整可见。

这次验证只证明交互原型成立。真实 Menu Bar／System Tray、窗口单实例、重新打开、退出、开机启动、多显示器和平台安全存储仍属于第 11 阶段的 Tauri 桌面壳验证。

独立设置窗口的验证结论已被 ADR-0011 取代；设置同窗路径尚未通过浏览器或实机验证。

## 进入正式实现的门禁

第 6～8 阶段的产品与交互定义已完成，可以开始第 11 阶段的 Tray 桌面壳；仍不得提前实现 Provider。

设置同窗变更不扩大产品范围，但改变了窗口拓扑。第 11 阶段必须先完成并补验该路径，再恢复“桌面壳实现完成”的结论。

Tray 实现应遵循以下顺序：

1. 在 Rust 侧使用 Tauri 2 System Tray API 建立系统图标、菜单和生命周期。
2. 使用同一份假数据驱动 macOS／Windows 紧凑入口和 Vue 窗口。
3. 验证主点击、Windows 右键菜单、主窗口、设置、重新打开和退出。
4. 验证窗口单实例、焦点、多显示器、开机启动、应用目录与最小 capability。
5. 双平台桌面壳通过后，才进入第一个 Provider 最小闭环。
