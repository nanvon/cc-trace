## 3. A 类：功能空白 —— Cycles 周期用量

cc-trace 当前没有对应视图（`src/views/` 只有 Compact／Conversations／Main／MainWindow／Onboarding／Settings／Timeline）。

### 3.1 cc-bar 侧事实（代码已确认）

新增三个文件，合计约 1700 行：

| 文件 | 规模 | 职责 |
|---|---|---|
| `../cc-bar/Core/Storage/QuotaCycleStore.swift` | +727 | 周期记录、额度段、重置采样、数据质量、漂移清理 |
| `../cc-bar/Core/Usage/CycleUsage.swift` | +490 | 周期归属聚合与用满预估 |
| `../cc-bar/Main/CycleStatsView.swift` | +470 | 宽卡＋周期时间轴＋历史四表切换 |

新增两份持久化：`quota-cycle-history.json`(v4)、`cycle-usage-rollup.json`(v3)。
后者与既有 `usage-rollup.json`、`conversation-rollup.json`、`scan-state.json` 共享同一代 `generationID`。

功能内核：按 Codex／Claude 主账号的真实重置窗口（5 小时 / 周）统计本机实际 Token 与 API 等值费用，
再用「本机用量 ÷（最高已用比例 − 起始基线）× 100」反推该周期的用满预估，配可信度四档与数据质量标记。
统计从功能上线首次启动开始，**不反推历史周期**，未观察到的周期不补造。
完整口径见 `../cc-bar/docs/产品需求.md` 的 Cycles 段与 `../cc-bar/docs/界面布局.md` §3.7。

### 3.2 迁移影响：比原版小，但需要新的边界事实

> 以下是基于两侧表结构的**静态推断**，未做原型验证。

cc-bar 为 Cycles 付出的相当一部分复杂度，来自它的用量聚合是 **day 粒度桶**（`usage-rollup.json` 的 `(day, app, model, speed)`），
切不出 5 小时周期，因此必须另建 `cycle-usage-rollup.json`，并在周期边界滚动时触发「受限重建」重新解析日志。

cc-trace 的 `usage_entries` 是**请求级事实表**，带 `occurred_at` 与 `api_equivalent_cost_nanos`
（表结构所有者见 [数据存储与用量索引](数据存储与用量索引.md)）。周期用量可由时间区间聚合直接得出。

由此推断的差异：

| cc-bar 的负担 | cc-trace 是否需要 |
|---|---|
| 第二套周期用量 rollup | 推断不需要，可由 `usage_entries` 按区间聚合 |
| 周期边界滚动触发的受限重建 | 推断不需要 |
| 四份缓存共享 `generationID` | 不需要，单库事务 |
| 周期边界与额度段的持久化 | **需要**，这是真正的新增事实 |

cc-trace 已有 `quota_events` 表（含 `resets_at`，schema v6），是周期边界的原始素材，但它记录的是「额度读数变化事件」，
不等于「周期记录＋额度段＋重置采样＋数据质量」这套结构化事实。

> **待确认**：周期边界从 `quota_events` 派生，还是新建独立表？前者省一份写入但要处理事件缺失（App 未运行期间）导致的边界空洞，
> 后者与 cc-bar 结构对齐但增加一处状态源。若假设错误，影响是 1～2 张表的设计与一次 schema 迁移。

> **待确认**：用满预估的公式、可信度四档边界、数据质量语义是否原样采纳。这些是 cc-bar 的产品判断，
> 不属于本仓库任何现有文档拥有的事实。若原样采纳，需要一份 ADR 明确它们由谁拥有。

### 3.3 前置条件

落地前建议先写 ADR，至少覆盖：周期边界的数据来源与派生规则、抖动容差（见第 4 节）、预估公式与可信度分档、
「不反推历史」的边界、Cycles 与侧边栏数据源过滤的关系（cc-bar 的做法是保留筛选项但不改变周期内容）。

## 4. B 类：跨端通用的坑 —— `resets_at` 抖动

**这一节即使不迁移 Cycles 也有价值。**

### 4.1 客观事实

Provider 返回的 `resets_at` 持续抖动。cc-bar 提交记录中的实测值：Claude 亚秒级，Codex 1～3 秒
（来源：`../cc-bar` 提交 `e4babc7` 说明，**cc-trace 侧未独立验证**）。这与实现语言无关。

cc-bar 为此连踩三次，代价逐次升高：

1. `e9a7b2c`（08-10）：抖动产生重复周期记录 → 周期匹配加 60 秒容差
2. `e4babc7`（08-15）：把每次返回的 `resets_at` 原样写入活跃周期边界，精确比较边界后每次刷新都被误判为「周期滚动」，
   触发受限重建从零解析最近 8 天日志。设计前提是「每天数次」，实际退化为每天约 720 次。
   修复方式是 5 秒边界漂移容差
3. `133c60c`（08-15）：相邻两个真实周期的边界各自带抖动，叠加后后一周期起点可能早于前一周期终点亚秒到数秒。
   原去重逻辑只要重叠 > 0 就判定重复，排序后较晚周期成为 base 吞掉较早周期的**整段历史且不可重建**。
   修复方式是 60 秒重叠阈值（真正的重复重叠接近整个窗口，与毛刺相差数千倍）

### 4.2 cc-trace 当前状态（代码已确认）

**目前不受影响。** `window_id` 是稳定常量（`codex.five-hour`／`codex.weekly`／`claude.model.<slug>`，
见 `src-tauri/src/providers/codex.rs` 的 `stable_window_id` 与 `claude.rs` 的 `scoped_window_id`），
不从 `resets_at` 派生；`record_quota_snapshot` 的去重条件是「同 `window_id` 下 `remaining_percent` 相同则跳过」，
`resets_at` 抖动不影响该判断，因此不会产生重复事件。

### 4.3 两项建议

- **做 Cycles 之前**，把「边界漂移容差」与「重叠去重阈值」两条规则写进设计。cc-bar 的三次修复说明：
  这类误判在周期语义下**不可逆**（被吞掉的历史无法从日志重建），事后修复救不回已丢数据
- 时间线页表格的 Reset 列直接展示事件时点的 `resets_at` 快照，同一周期内相邻行会出现秒级差异。
  > **待确认**：这是否构成可见的展示问题，需要在真实数据下看一眼再决定是否做显示层归一。若需要处理，
  > 影响范围仅限时间线页展示，不涉及存储口径

## 6. D 类：不适用或已有相反决策

| cc-bar 改动 | 结论 | 理由 |
|---|---|---|
| `4afa833` 额度持久化批量合并（`QuotaPersistenceCoordinator`） | **不建议直搬** | [性能与功耗优化方案](性能与功耗优化方案.md) §1.2 已判断「暂不建议两个 Provider 缓存写合并」，理由是延迟写降低崩溃后快照新鲜度。该决策依然成立。可留档的是其中「用单调序列号裁决乱序提交、旧快照不得覆盖新快照」的做法 |
| `53e7ae9` 主 Provider 关闭时跳过凭据与额度链路 | **不适用** | 前提是 cc-bar「设置 → 账号」的 Provider 开关。cc-trace 设置项中没有该开关（只有统计服务可见性 `usage_service_visibility`），见 [产品范围](产品范围.md)「基础设置」 |
| `26afa8a` Antigravity 复用进程探测 | **不适用** | Antigravity 在 [产品范围](产品范围.md)「明确不做」内 |
| `a441eff` JSONL 枚举一次取 mtime/size | **方向已覆盖，实现不通用** | cc-trace 侧对应议题见 [性能与功耗优化方案](性能与功耗优化方案.md) 的目录遍历与前缀校验项，结论是「先测再决定」 |
| `e4babc7` 中的 ISO8601 手写快路径 | **线索，未验证** | cc-bar 实测该解析占整轮扫描 CPU 一半以上（CFDateFormatter 通用状态机）。cc-trace 用 `chrono::DateTime::parse_from_rfc3339`，理论开销远低于 CFDateFormatter，**是否同样构成热点未验证**。建议仅作为性能剖析时的一个观测点，不作为优化项 |

已在 [产品范围](产品范围.md) 中定性、本区间未改变其性质的能力：多 Codex 账号导入、桌面悬浮窗、自动更新（后续版本评估）；
Antigravity、Codex Reset Credits、Claude CLI 兜底与 delegated refresh（明确不做）。

`../cc-bar/docs/历史用量数据补录指南.md` 是一次性数据修复手册（配合 cc-switch 找回被 Claude Code `cleanupPeriodDays` 清理掉的日志），
不是产品功能，不构成迁移项。

## 7. 建议顺序

按「独立可验证、代价递增」排列。顺序是建议，不是排期承诺。

1. **时间线页三个视觉细项**（C 类）—— 纯前端，把 2026-08-10 那次对齐收尾，取值先落 [设计方向与状态规范](设计方向与状态规范.md)
2. **重算进度反馈**（C 类）—— 后端进度事件 ＋ 前端订阅，与现有扫描状态展示同构，独立可验证
3. **Cycles**（A 类）—— 单独立项。先 ADR 后代码，前置条件见 §3.3

第 4 节的抖动结论不单独排期：它是做 Cycles 时的**前置输入**，以及时间线页展示层的一个待观察项。
