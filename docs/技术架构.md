# CC Trace 技术架构

> 状态：首版基线
> 目标版本：`0.1.x`
> 基线日期：2026-07-25

## 技术选择

| 层 | 选择 |
|---|---|
| 桌面容器 | Tauri 2 |
| 前端 | Vue 3、TypeScript、Vite |
| 状态 | Pinia |
| 路由 | Vue Router |
| 国际化 | Vue I18n |
| 样式 | CSS Variables + 原生 CSS，首版不引入重型 UI 框架 |
| 原生与业务核心 | Rust |
| 包管理 | pnpm |
| Rust 管理 | Cargo |

Tauri 官方当前提供 Vue + TypeScript 模板，首版以官方 `create-tauri-app` 生成结果为起点，再按本文件收敛目录和权限。

## 分层与职责

```text
Vue UI
  ↓ typed invoke / event
Tauri command 边界
  ↓
Rust App Core
  ├── Providers
  ├── Scheduler
  ├── Storage
  └── Platform Adapters
  ↓
Codex / Claude Code 凭据来源与 Provider 接口
```

### Vue

- 页面、组件、主题、国际化和无障碍。
- 展示额度快照、刷新状态和脱敏账号信息。
- Pinia 只保存当前展示状态，不实现 Provider 请求、凭据读取或持久化规则。
- 不直接开放通用文件系统、Shell、任意 HTTP 或安全存储能力。

### Tauri command 边界

- 校验前端输入。
- 调用 Rust 用例并返回明确 contract。
- 将内部错误映射成稳定、可展示的错误类型。
- 所有载荷必须可序列化且不包含秘密。

首版 command：

```text
app_get_status
quota_get_snapshot
quota_refresh
settings_read
settings_update
window_open_main
app_quit
```

首版事件：

```text
quota://updated
quota://refresh-state
settings://updated
```

只有确实需要后台主动推送时才使用事件；普通读取优先使用 command，避免重复状态源。

### Rust App Core

- `providers`：凭据发现、Provider 请求、响应解析和标准化。
- `scheduler`：自动刷新、请求合并、节流、429 退避和 Provider 隔离。
- `storage`：设置、最新有效快照、Schema Version、原子写入和损坏恢复。
- `platform`：Tray、窗口、安全存储、开机启动、系统路径和平台差异。
- `contracts`：跨 command 边界使用的脱敏 DTO。

业务核心不依赖 Vue 组件结构，不把 `isMac` / `isWindows` 判断散落在前端业务代码。

## 核心 contracts

首版至少定义：

```text
ProviderId
CredentialStatus
QuotaWindow
QuotaSnapshot
ProviderSnapshot
RefreshState
SnapshotFreshness
AppError
Settings
AppStatus
```

`ProviderSnapshot` 同时包含数据与状态，使一个 Provider 可以成功、另一个 Provider 可以失败。前端不得通过空值猜测 `loading`、`stale` 或 `error`。

## 数据与恢复

CC Trace 只维护自己的数据：

```text
settings.json
quota-cache.json
logs/
```

规则：

- 每个持久化文件包含 `schemaVersion`。
- 使用临时文件写入、同步并原子替换，写入失败保留上一份有效文件。
- 设置损坏时回退到安全默认值，并保留可诊断但不含秘密的错误。
- 额度缓存损坏时删除逻辑引用并重新获取，不尝试读取 cc-bar 缓存。
- 缓存只保存展示所需的脱敏快照，不保存凭据。
- 首版不创建 Usage、Conversation、Pricing 或 Timeline 数据文件。

## 凭据与权限

- Codex、Claude Code 凭据由 Rust 平台适配层按只读、最小范围发现。
- 凭据只在完成 Provider 请求所需的生命周期内存在于 Rust 内存。
- 不通过 command、event、前端日志或普通应用日志输出秘密。
- 首版不提供账号导入，因此不新增 Provider 凭据写入。
- Tauri capabilities 从默认最小集合开始，新增每项权限时记录对应用户功能。
- 前端不获得通用 `fs`、`shell`、`http` 或 Stronghold 访问能力。

## 刷新模型

- 每个 Provider 独立维护刷新状态和最新有效快照。
- 同一 Provider 的并发刷新合并为一个任务。
- 自动刷新加入轻微抖动，避免固定时刻集中请求。
- 429 按 Provider 独立退避，并优先采用服务端 `Retry-After`。
- 网络或临时错误保留最新有效快照并标记 `stale` 或 `offline`。
- 凭据无效、协议不兼容等错误不能被伪装成网络离线。

## UI 启动顺序

1. Vue 读取 Rust 提供的应用状态与设置。
2. Rust 读取 CC Trace 自己的最新有效快照。
3. 界面先展示缓存并标记新鲜度。
4. 调度器按策略刷新两个 Provider。
5. 每个 Provider 独立更新状态。
6. 用户可随时手动刷新或打开主窗口。

## 发布边界

- 开发阶段从 `0.1.0` 开始。
- 第一阶段只建立本地开发与 CI 基线，不承诺公开发布。
- macOS 签名、公证、Windows 代码签名、安装器与自动更新在公开分发前单独设计和验收。
- CI 和构建不能依赖相邻的 `../cc-bar` 仓库；旧仓库只供人工查阅与 Fixture 提取。
- macOS 与 Windows 分别构建平台产物，不做跨平台交叉打包假设。

## 实施顺序

1. 初始化官方 Tauri 2 + Vue 3 + TypeScript 模板。
2. 接入 Pinia、Vue Router、Vue I18n、主题和品牌资源。
3. 建立 contracts、commands 与最小 capability。
4. 使用假数据验证 Tray、紧凑入口、主窗口与双平台身份隔离。
5. 打通一个 Provider 的凭据发现、额度请求、缓存和展示闭环。
6. 扩展到第二个 Provider，并验证故障隔离。
7. 完成首版设置、状态、错误恢复和双平台验收。

正式页面实现必须以确认后的信息架构和交互原型为输入；工程初始化不等于提前实现业务页面。
