## 分层与职责

```text
Vue UI
  ↓ typed invoke / event
Tauri command 边界
  ↓
Rust App Core
  ├── Providers
  ├── Scheduler
  ├── Storage
  └── Platform Adapters
  ↓
Codex / Claude Code 凭据来源与 Provider 接口
```

### Vue

- 页面、组件、主题、国际化和无障碍。
- 展示额度快照、刷新状态和脱敏账号信息。
- Pinia 只保存当前展示状态，不实现 Provider 请求、凭据读取或持久化规则。
- 不直接开放通用文件系统、Shell、任意 HTTP 或安全存储能力。

### Tauri command 边界

- 校验前端输入。
- 调用 Rust 用例并返回明确 contract。
- 将内部错误映射成稳定、可展示的错误类型。
- 所有载荷必须可序列化且不包含秘密。

首版 command：

```text
app_get_status
quota_get_snapshot
quota_refresh
settings_read
settings_update
onboarding_complete
window_open_main
window_open_settings
window_open_onboarding
window_open_compact
window_hide_compact
app_quit
```

`window_open_main` 与 `window_open_settings` 表达两个用户意图，但都复用 `main` 窗口：前者切换到额度总览，后者切换到设置视图。这样紧凑面板、原生菜单和快捷键不需要知道 Vue 路由，同时不会重新引入独立设置窗口。

代码已按 [ADR-0011](决策/ADR-0011-设置并入主窗口.md) 收敛：Tauri 不再预创建 `settings` 窗口，两个 command 均复用 `main`，前端在主窗口持久外壳内切换子路由。本轮改造尚未运行自动化检查或实机验证。

`window_open_compact` 与 `window_hide_compact` 服务首次启动完成后的跳转、`Esc` 与 `⌘W`／`Ctrl+W`；`window_hide_compact` 同时记录隐藏时刻，供系统区域图标的主点击去抖使用，因此紧凑面板的隐藏路径只有这一条。

debug 构建额外提供 `dev_set_scenario`，用于切换桌面壳的合成验证场景。它由 `#[cfg(debug_assertions)]` 包裹，release 构建里不存在，见 [ADR-0009](决策/ADR-0009-合成数据下沉Rust并提前使用正式契约.md)。

首版事件：

```text
quota://updated
quota://refresh-state
settings://updated
navigation://main
```

业务数据只有确实需要后台主动推送时才使用事件；普通读取优先使用 command，避免重复状态源。`navigation://main` 是平台入口把一次性导航意图送到既有主窗口的例外，不承载业务数据。

`quota://refresh-state` 是活动维度的**唯一**来源，不存在第二个刷新事件。`quota://updated` 的载荷是完整的 `QuotaState`，前端不做增量合并。

`navigation://main` 只发给 `main` 窗口，载荷为 `quota` 或 `settings`。它只表达一次性的导航意图，不进入 Pinia、设置文件或额度缓存，也不能成为业务状态源。`window_open_main` 与 `window_open_settings` 复用这一个平台到主窗口的导航入口；主窗口内部“返回额度”直接使用同一条 Vue Router 目标路由。

### Rust App Core

- `app`：`AppCore` —— 设置、Provider 运行时与刷新调度的唯一持有者，也是事件广播的唯一出口。
- `providers`：凭据发现、Provider 请求、响应解析和标准化。
- `scheduler`：自动刷新、请求合并、节流、429 退避和 Provider 隔离。
- `storage`：设置、最新有效快照、Schema Version、原子写入和损坏恢复。
- `platform`：Tray、窗口、开机启动、原生文案、系统路径和平台差异。
- `contracts`：跨 command 边界使用的脱敏 DTO。

所有 command 都经过 `AppCore`，因此界面永远只有一个状态源。

业务核心不依赖 Vue 组件结构，不把 `isMac` / `isWindows` 判断散落在前端业务代码。

## 核心 contracts

首版至少定义：

```text
ProviderId
CredentialStatus
QuotaWindow
QuotaSnapshot
ProviderSnapshot
RefreshState
SnapshotFreshness
ProviderAvailability
AppError
Settings
OnboardingState
AppStatus
```

`ProviderSnapshot` 同时包含数据与状态，使一个 Provider 可以成功、另一个 Provider 可以失败。

`RefreshState`、`SnapshotFreshness` 和 `ProviderAvailability` 的取值与语义由 [状态与错误模型](状态与错误模型.md) 定义；额度字段与标准化规则由 [额度领域模型](额度领域模型.md) 定义。本文件只规定它们在契约边界上的形态：

- 三个状态维度必须各自独立序列化，不得压成一个互斥枚举。
- 前端不得通过空值猜测状态。
- `AppError` 只承载可展示的错误分支（凭据类／协议类），不替代 `ProviderAvailability`。
- 所有载荷可序列化且不含秘密、端点原文、文件路径或凭据内容。

契约实现真值在 `src-tauri/src/contracts/`，前端镜像在 `src/features/quota/contracts.ts` 与 `src/features/settings/contracts.ts`，改一侧必须同时改另一侧。三维契约在第 11 阶段就是最终形态，第 12 阶段接入真实 Provider 时不再改动，见 [ADR-0009](决策/ADR-0009-合成数据下沉Rust并提前使用正式契约.md)。

### Provider 抽象

`providers::QuotaProvider` 定义一个 Provider 的额度来源，`ProviderFetchOutcome` 定义它的全部可能结局，每个分支对应 [状态与错误模型](状态与错误模型.md) 第 4 节的一类失败来源。

第 11 阶段只有 `providers::synthetic` 一个实现，产出合成快照。第 12 阶段**只替换本模块内部的实现**：trait、结局类型、契约、调度、命令与前端都不变。

## 窗口与首次启动

首版共三个窗口，全部由 Tauri 配置预创建并保持单实例；精确尺寸见 [设计方向与状态规范](设计方向与状态规范.md) 第 5.3 节。

| 窗口 label | 职责 | 初始状态 | 关键行为 |
|---|---|---|---|
| `main` | 额度总览与设置 | 隐藏 | 默认显示额度总览；设置为同窗二级视图；重复打开时聚焦已有实例；关闭时隐藏，进程继续驻留 |
| `compact` | 紧凑额度面板 | 隐藏 | 无装饰、不可缩放、置顶、不进任务栏、失焦隐藏 |
| `onboarding` | 首次启动 | 隐藏 | 只在完成标记缺失时打开；完成后隐藏并打开紧凑面板 |

`main` 内部使用 Vue Router 在额度总览与设置之间导航，但不持久化最后停留视图：

- “打开 CC Trace”与二次启动聚焦主窗口时显示额度总览。
- “设置”入口与 `⌘,`／`Ctrl+,` 聚焦同一个主窗口并显示设置视图。
- 设置视图返回额度时不创建、销毁或缩放原生窗口。
- 当前目标由 `navigation://main` 传递；只有当前可见视图进入焦点序列。

首次启动状态：

- `OnboardingState` 至少包含 `completed` 与 `completedAt`。
- 完成标记保存在 CC Trace 自己的 `settings.json`，与其他偏好共用同一个 `schemaVersion`。
- 未完成时，用户主动打开应用仍进入首次启动窗口；用户暂时关闭不写入完成标记。
- `onboarding_complete` 是唯一写入完成标记的入口；写入失败时保持未完成并明确提示。
- 首版不读取任何外部或 Swift 版 cc-bar 的 Onboarding 标记。
- `onboarding` 窗口、`window_open_onboarding` 与 `onboarding_complete` 已实现，完成标记落在 `settings.json`。

## 数据与恢复

CC Trace 只维护自己的数据：

```text
settings.json
quota-cache.json
logs/
```

`logs/` 的级别、格式、轮转与脱敏规则见 [日志与诊断](日志与诊断.md)。

规则：

- 每个持久化文件包含 `schemaVersion`。
- 使用临时文件写入、同步并原子替换，写入失败保留上一份有效文件。
- 设置损坏时回退到安全默认值，并保留可诊断但不含秘密的错误。
- 额度缓存损坏时删除逻辑引用并重新获取，不尝试读取 cc-bar 缓存。
- 缓存只保存展示所需的脱敏快照，不保存凭据。
- Provider 身份变化时丢弃该 Provider 的缓存条目与退避状态，界面不得展示上一个身份的额度，见 [额度领域模型](额度领域模型.md) 第 4.1 节。
- 首版不创建 Usage、Conversation、Pricing 或 Timeline 数据文件。

落地状态：`settings.json` 已在第 11 阶段实现，含 `schemaVersion`、原子写入、损坏与版本过高时回退安全默认值（原文件改名为 `settings.json.corrupt` 留作诊断，该文件不含任何秘密），理由见 [ADR-0010](决策/ADR-0010-最小设置持久化提前落地.md)。`quota-cache.json` 与 `logs/` 属第 12／13 阶段，尚未创建，也不预留空实现。

## 凭据与权限

- Codex、Claude Code 凭据由 Rust 平台适配层按只读、最小范围发现。
- 凭据只在完成 Provider 请求所需的生命周期内存在于 Rust 内存。
- 不通过 command、event、前端日志或普通应用日志输出秘密。
- 首版不提供账号导入，因此不新增 Provider 凭据写入。
- Tauri capabilities 从默认最小集合开始，新增每项权限时记录对应用户功能。
- 前端不获得通用 `fs`、`shell`、`http` 或 Stronghold 访问能力。

当前 capability（`src-tauri/capabilities/default.json`）：

| 权限 | 对应的用户功能 |
|---|---|
| `core:default` | invoke 与事件订阅；前端与 Rust 的全部通信 |
| `core:window:allow-hide` | `⌘W`／`Ctrl+W` 关闭主窗口或首次启动窗口时应用继续驻留系统区域，而不是退出 |

Rust 侧还启用了 `tauri` 的 `macos-private-api` feature，用于紧凑面板的透明窗口与 popover 材质（`tauri.conf.json` 的 `macOSPrivateApi` 与 `windowEffects`）。代价是不能上架 Mac App Store；CC Trace 走独立分发，可以接受。

## 刷新模型

- 每个 Provider 独立维护刷新状态和最新有效快照。
- 同一 Provider 的并发刷新合并为一个任务。
- 自动刷新加入轻微抖动，避免固定时刻集中请求。
- 429 按 Provider 独立退避，并优先采用服务端 `Retry-After`。
- 网络或临时错误保留最新有效快照并标记 `stale` 或 `offline`。
- 凭据无效、协议不兼容等错误不能被伪装成网络离线。

### 首版参数基线

用户可见的自动刷新间隔候选值和默认值属于产品决策，见 [产品范围](产品范围.md) “基础设置”。以下工程参数为首版基线：

| 参数 | 首版值 | 说明 |
|---|---|---|
| 自动刷新抖动 | 间隔的 ±10% | 避免两个 Provider 固定同刻请求 |
| 同一 Provider 手动刷新最小间隔 | 30 秒 | 期间的重复触发合并到当前任务，不排队重发 |
| 单次 Provider 请求超时 | 15 秒 | 超时归为网络类失败 |
| 429 退避 | 优先 `Retry-After`；缺失时 60s → 120s → 300s，上限 15 分钟 | 按 Provider 独立计算，成功后重置 |
| 网络与临时错误退避 | 30s → 60s → 120s，上限 5 分钟 | 按 Provider 独立计算，成功后重置 |
| 快照降级为 `stale` | 快照年龄超过当前自动刷新间隔的 2 倍 | 即使上次刷新成功也降级，并触发一次刷新 |
| 启动与唤醒 | 读取缓存后立即刷新一次 | 系统唤醒后若快照年龄超过间隔，同样刷新一次 |
| token 刷新提前量 | Codex `300` 秒、Claude Code `30` 秒 | 见 [额度领域模型](额度领域模型.md) 第 5.2 节 |

退避期内不得发起真实请求，但必须向界面提供可再次尝试时间；**手动刷新不得绕过退避**。以上数值在 Provider 最小闭环验证后可以调整，调整必须同步本表，不允许只改代码常量。

## UI 启动顺序

1. Vue 读取 Rust 提供的应用状态与设置。
2. Rust 读取 CC Trace 自己的最新有效快照。
3. 界面先展示缓存并标记新鲜度。
4. 调度器按策略刷新两个 Provider。
5. 每个 Provider 独立更新状态。
6. 用户可随时手动刷新或打开主窗口。

## 发布边界

- 开发阶段从 `0.1.0` 开始。
- 第一阶段只建立本地开发与 CI 基线，不承诺公开发布。
- macOS 签名、公证、Windows 代码签名、安装器与自动更新在公开分发前单独设计和验收。
- CI 和构建不能依赖相邻的 `../cc-bar` 仓库；旧仓库只供人工查阅与 Fixture 提取。
- macOS 与 Windows 分别构建平台产物，不做跨平台交叉打包假设。
