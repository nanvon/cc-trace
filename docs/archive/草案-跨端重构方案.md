## 1. 项目定位

新应用独立于当前 cc-bar：

- 使用新的 Git 仓库。
- 使用新的应用标识、数据目录和发布体系。
- 不复制 Swift / SwiftUI 工程进入新仓库。
- 不兼容、不迁移、不删除当前 cc-bar 自己保存的数据。
- 不默认要求逐项复刻当前 cc-bar 已有功能。
- 重新定义产品范围、信息架构、视觉语言和交互方式。
- 从第一天同时面向 macOS 和 Windows。

当前 cc-bar 继续作为独立应用保留。旧仓库用于：

- 继续维护和发布现有 Swift 版本。
- 查阅已经验证的 Provider 行为、额度语义和错误处理经验。
- 查阅本地日志扫描、聚合、计价和去重规则。
- 提供问题样本、脱敏 Fixture 和结果对照。
- 评估哪些旧功能值得进入新产品。

旧仓库是参考资料，不是新应用的工程基础或发布主线。

## 2. 已确认的核心决策

| 事项 | 决策 |
|---|---|
| 代码仓库 | 创建独立新仓库 |
| 产品关系 | 新应用独立开发，不作为 Swift 版原地升级 |
| 目标平台 | macOS、Windows |
| 桌面容器 | Tauri 2 |
| 前端技术 | Vue 3 + TypeScript + Vite |
| 原生与业务核心 | Rust |
| 前端状态 | Pinia |
| 页面路由 | Vue Router |
| 工程起点 | 先建立单桌面应用，按真实复用需求再拆 workspace |
| 产品范围 | 重新定义；旧版功能不自动进入首版 |
| 设计策略 | 从零设计信息架构、页面、视觉和交互 |
| 应用身份 | 使用新的 Bundle Identifier、Windows Application ID 和系统注册标识 |
| 数据原则 | 新应用使用独立存储，不读取或迁移旧 cc-bar 应用数据 |
| 外部数据源 | 可以读取 Codex / Claude Code 自身凭据和原始日志 |
| 秘密存储 | 只通过 Rust 和系统安全存储访问，不进入 Vue 层 |
| 版本体系 | 开发阶段使用 `0.x`，首次正式发布为 `1.0.0` |
| 旧 Swift 版本 | 保留在当前 cc-bar 仓库，不复制进新仓库 |
| 发布体系 | 新仓库独立构建和发布 macOS、Windows 版本 |

AppKit 是 macOS UI 框架，Swift 是语言，当前体验问题不能简单归因于 Swift。选择 Tauri 的原因是希望 macOS 和 Windows 共用主要页面、业务状态和核心逻辑，同时允许平台适配层分别处理系统托盘、安全存储、开机启动和窗口行为。

### 3.2 可以参考

新应用可以参考当前 cc-bar 中已经验证的知识：

- Codex、Claude Code 凭据发现方式。
- Provider 请求、额度字段和窗口语义。
- token 续期、请求节流和 429 退避。
- 网络失败时保留快照的原则。
- Codex、Claude Code 原始日志位置和记录格式。
- JSONL 增量扫描、截断处理和去重规则。
- Token、Fast、Pricing、Conversation 等计算口径。
- macOS 菜单栏、悬浮窗和生命周期的已知问题。
- 当前产品中真实有效或已经证明无效的交互经验。

必要时可以从旧仓库提取脱敏 Fixture、协议说明和测试预期，但不能未经判断地复制旧模块结构。

### 3.3 不继承

新应用不继承以下内容：

- 当前仓库历史和分支结构。
- Swift / SwiftUI / AppKit 工程结构。
- 当前 Bundle Identifier 和应用数据目录。
- 当前 UserDefaults、缓存和索引格式。
- 当前安全存储 service namespace。
- 当前开机启动注册标识。
- 当前版本号和 Release 流程。
- 当前页面结构、导航、卡片布局和视觉规范。
- “旧版有的功能首版必须全部实现”的默认前提。

### 3.4 不建立迁移关系

新应用与当前 cc-bar 之间没有应用数据迁移链：

- 新应用不读取旧设置。
- 新应用不读取旧额度缓存。
- 新应用不读取旧统计聚合和扫描索引。
- 新应用不导入旧版保存的其他账号。
- 新应用不继承旧悬浮窗位置。
- 新应用不继承旧 Onboarding 状态。
- 新应用不读取、覆盖或删除旧版专用安全存储项。
- 新应用不会自动卸载旧应用。

两个应用应能在同一台机器上独立安装、运行和卸载。

## 4. 新产品范围

新应用的功能范围由新产品定义决定，不再由旧代码反推。所有候选能力必须明确归入以下状态之一：

- 首版必须。
- 首版简化。
- 后续版本。
- 明确不做。

只有被确认进入首版的能力，才进入设计、实现和验收清单。

### 4.1 首版核心任务

首版优先验证以下用户任务：

1. 在 macOS 菜单栏或 Windows 系统托盘快速看到额度状态。
2. 打开紧凑入口后，立即判断哪个 Provider 接近额度限制。
3. 查看 Codex、Claude Code 的主要额度、重置时间和刷新状态。
4. 安全读取本机现有 Provider 凭据，不向 Vue 暴露秘密。
5. 手动或自动刷新额度，并正确处理失败、旧快照和 429 退避。
6. 在主窗口完成必要设置和状态检查。
7. 使用同一套主要代码在 macOS、Windows 安装和运行。

### 4.2 建议首版范围

- macOS Menu Bar。
- Windows System Tray。
- 常驻图标及平台等价的紧凑额度信息。
- Codex、Claude Code 自动发现。
- Codex、Claude Code 主要额度和必要的专项额度。
- 剩余百分比、重置时间和最近刷新时间。
- live、stale、offline、loading、error 状态。
- 手动刷新。
- 自动刷新间隔。
- 请求节流和 429 退避。
- Provider 失败时保留新应用已有快照。
- 一个 Provider 失败不影响其他 Provider。
- 新版独立本地缓存。
- 基础设置。
- 中文、英文和跟随系统。
- 浅色、深色和跟随系统。
- 开机自动启动。
- 版本信息。
- 首次启动的最小引导或状态检查。

### 4.3 首版后再评估的能力

以下能力不因旧版存在而自动进入首版：

- 本地用量汇总。
- Token 和费用趋势。
- Conversations 列表与详情。
- Timeline 或额度变化历史。
- Pricing 目录和 API 等值费用。
- 其他 Codex 账号导入与管理。
- 桌面悬浮窗。
- 隐私模式。
- 复杂日期范围和自定义筛选。
- 高级诊断信息。
- 完整的模型、速度档位和 Fast 拆分。

进入实现前，应在 `产品范围.md` 中逐项确认其优先级、用户价值、数据来源和验收标准。

### 4.4 明确非目标

除非产品范围另行确认，首版不做：

- Swift 版数据迁移。
- Swift 版页面复刻。
- 旧版功能的一对一模块翻译。
- 应用内 Provider 登录。
- 浏览器 Cookie 自动导入。
- 通过 WebView 抓取 Provider 网站页面。
- 为兼容旧版而保留无价值字段或设置。
- 旧版和新版之间的实时数据同步。
- 自动卸载或清理旧应用。

## 5. 数据边界

### 5.1 三类数据必须分开

```text
旧 cc-bar 应用数据
  设置、缓存、Rollup、扫描索引、导入账号、窗口位置
  → 不读取、不迁移、不修改

Codex / Claude Code 外部数据
  当前凭据、原始会话日志、项目日志
  → 经产品授权后作为新应用数据源读取

新应用数据
  新设置、新缓存、新索引、新历史和新安全存储项
  → 由新应用独立创建和维护
```

### 5.2 明确不兼容的旧版数据

| 旧版数据 | 新应用处理 |
|---|---|
| `quota-cache.json` | 不读取；首次刷新重新建立快照 |
| `quota-history-today.json` | 不读取；额度变化从新应用启用后开始记录 |
| `usage-rollup.json` | 不读取；若实现用量统计，则从原始日志重建 |
| `conversation-rollup.json` | 不读取；若实现对话分析，则从原始日志重建 |
| `pricing-catalog.json` | 不读取；使用新应用自己的远端或内置目录 |
| `scan-state.json` | 不读取；若实现日志扫描，则首次全量索引 |
| Swift UserDefaults | 不读取；使用新版默认设置 |
| 其他 Codex 账号记录 | 不迁移；需要时由用户重新导入 |
| 悬浮窗位置 | 不迁移；使用新版默认位置 |
| Onboarding 标记 | 不迁移；新应用独立完成首次启动流程 |
| 旧版专用安全存储项 | 不读取、不修改、不删除 |

### 5.3 可以读取的外部数据

下列内容不是旧 cc-bar 应用数据，可以作为新应用的产品数据源：

- Codex 当前凭据文件或系统安全存储。
- Claude Code 当前凭据文件或系统安全存储。
- Codex sessions 和 archived sessions 原始 JSONL。
- Claude Code projects 原始日志。
- Provider 实时接口响应。
- 新应用自己的远端价格目录。

读取外部数据仍需遵守：

- 最小权限。
- 只读取完成当前功能所需的数据。
- 秘密只留在 Rust 层。
- 普通日志不得输出秘密。
- 不修改外部日志源。
- 写回凭据必须是产品明确需要且经过设计的行为。

### 5.4 首次启动

新应用首次启动时：

1. 创建独立数据目录。
2. 写入新应用默认设置。
3. 检查用户授权范围内的 Provider 凭据。
4. 获取首批额度数据。
5. 建立新应用自己的缓存。
6. 若首版包含本地用量，则从原始日志执行首次索引。
7. 不访问旧 cc-bar 应用数据目录。
8. 不修改旧应用及其安全存储项。

旧额度缓存和旧额度变化历史无法重建。原始会话日志仍存在时，本地用量和对话数据可以重新计算，但首次全量索引可能较慢。

### 5.5 新版存储仍需版本管理

不兼容旧 cc-bar，不代表新应用不需要自己的升级能力。新应用的第一个持久化格式必须具备：

- `schemaVersion`。
- 明确的默认值。
- 原子写入。
- 写入失败不破坏上一份有效快照。
- 损坏检测和安全回退。
- 可重建数据与不可重建数据分离。
- 新应用未来版本之间的升级入口。

示意：

```json
{
  "schemaVersion": 1,
  "updatedAt": "2026-01-01T00:00:00Z",
  "data": {}
}
```

## 6. 应用身份与共存

为了避免系统把新应用当作旧版升级，新应用必须使用独立身份：

- 新 Bundle Identifier。
- 新 Windows Application ID。
- 新应用数据目录。
- 新设置 namespace。
- 新 Keychain / Credential Manager service namespace。
- 新开机启动注册标识。
- 新日志目录。
- 新缓存目录。
- 新安装包标识。

开发和验收阶段，新旧应用应能共存。若最终继续使用 CCBar 品牌，也不能把“不迁移数据的新应用”包装成无损原地升级。

旧应用的卸载和旧数据清理不属于新应用职责。

## 7. 技术架构

### 7.1 分层

```text
Vue UI
  ↓ Tauri command / event
Rust App Core
  ├── Provider
  ├── Scheduler
  ├── Usage Scanner（按产品范围启用）
  ├── Storage
  └── Platform Adapter
  ↓
脱敏后的 QuotaSnapshot / UsageSnapshot / Settings / AppState
  ↓
Vue UI
```

职责边界：

- Vue：页面、交互、展示状态、Pinia、路由、主题和国际化。
- Rust：凭据、Provider 请求、调度、缓存、日志扫描和业务计算。
- Tauri：command、event、权限和窗口桥接。
- Platform Adapter：Tray、系统安全存储、开机启动、窗口和路径差异。

### 7.2 安全边界

Vue 层不能取得：

- access token。
- refresh token。
- session Cookie。
- Codex auth 原文。
- Claude Code credential 原文。
- Keychain 或 Credential Manager 原始值。

Vue 层只能取得完成页面展示所需的：

- 脱敏账号信息。
- 额度快照。
- 统计结果。
- 设置。
- 刷新和错误状态。

Tauri capabilities 遵守最小权限原则，不开放通用文件系统、Shell 或任意网络访问给 Vue。

### 7.3 Command 和事件

首版 command 按确认后的产品范围收敛，不预先为所有旧功能设计接口。

建议起点：

```text
quota.get_snapshot
quota.refresh
settings.read
settings.update
app.get_status
window.open_main
app.quit
```

若后续确认本地用量能力，再增加：

```text
usage.get_overview
usage.get_conversations
usage.get_conversation_detail
usage.scan
```

后台变化通过受控事件发布：

```text
quota://updated
quota://refresh-state
settings://updated
usage://updated
```

事件载荷必须使用明确的 contract，并且不包含秘密。

## 9. 平台边界

## 10. 新设计原则

新应用不继承当前 Swift 版设计规范和页面布局。

设计阶段先确认：

- 核心用户任务。
- 信息优先级。
- 紧凑入口和主窗口的职责。
- macOS 菜单栏与 Windows 托盘的等价关系。
- Loading、Empty、Error、Stale、Offline 状态。
- 键盘、焦点和无障碍。
- 长账号名、长模型名和双语布局。
- 浅色、深色和系统外观。
- 动效和反馈原则。

体验目标：

- 打开紧凑入口后能立即识别额度风险。
- 高频信息优先，诊断和低频设置按需展开。
- 高信息密度下仍保持明确层级。
- 不依赖大量同质卡片和无意义装饰分割内容。
- 刷新、错误恢复、展开和窗口出现有清晰反馈。
- 鼠标、触控板和键盘都可完成主要操作。
- macOS、Windows 可以有平台差异，但不因此删减核心任务。

旧截图只用于识别内容和体验问题，不作为视觉回归基线。

## 11. 实施顺序

### 11.1 定义新产品

- 确认产品名称和一句话定位。
- 确认目标用户和核心任务。
- 建立首版、后续、删除三类能力清单。
- 明确新应用与 cc-bar 的关系。
- 明确非目标和验收标准。

在产品范围确认前，不根据旧版目录直接搭建业务模块。

### 11.2 建立新设计基线

- 信息架构。
- 核心流程。
- 紧凑入口线框。
- 主窗口线框。
- 设置和首次启动线框。
- 典型、极端、空数据和错误状态。
- 视觉方向、tokens、基础组件和动效原则。
- macOS、Windows 平台差异。

完成交互原型并确认后再进入正式页面实现。

### 11.3 验证双平台桌面壳

- 从新仓库创建 Tauri 2 工程。
- macOS、Windows 构建同一个桌面入口。
- 使用假数据验证 Tray、紧凑入口和主窗口。
- 验证系统安全存储。
- 验证开机启动。
- 验证应用身份、数据目录和权限相互隔离。
- 验证新旧应用能够并行运行。

### 11.4 打通 Provider 最小闭环

1. 读取一个 Provider 的外部凭据。
2. 在 Rust 层请求并标准化额度。
3. 将脱敏快照通过 command 传给 Vue。
4. 在紧凑入口和主窗口展示。
5. 支持手动刷新。
6. 写入和读取新版缓存。
7. 处理错误和旧快照保留。
8. 在 macOS、Windows 验证同一闭环。

### 11.5 实现首版能力

按确认后的产品范围纵向实现，每个切片同时完成：

- Rust 核心。
- Tauri command / event。
- Vue 页面和交互。
- Loading、Empty、Error、Stale 状态。
- 单元或集成测试。
- macOS、Windows 验收。

不按旧 Swift 模块顺序机械翻译。

### 11.6 首次初始化

- 创建新应用目录。
- 写入默认设置。
- 建立新版缓存。
- 建立 Schema Version。
- 验证损坏数据的安全回退。
- 若包含本地用量，完成首次全量索引和进度反馈。
- 验证全过程不读取或修改旧 cc-bar 应用数据。

### 11.7 发布验证

- macOS 安装、签名、公证。
- Windows 安装、签名。
- 两个平台的启动、重新打开、退出和卸载。
- 两个平台的系统区域入口。
- 两个平台的开机启动。
- 两个平台的权限、安全存储和数据目录。
- 新应用自身后续版本的升级基础。
- 与旧应用并行运行时互不影响。

## 13. 首版验收标准

首版验收项最终以 `产品范围.md` 为准，至少满足：

### 13.1 产品

- macOS、Windows 均能安装、启动、重新打开和退出。
- Menu Bar / System Tray 可用。
- 已进入首版范围的 Provider 能正确发现和展示额度。
- 手动刷新、自动刷新、节流和 429 退避工作正常。
- Provider 失败时保留新应用已有快照。
- Loading、Empty、Error、Stale、Offline 状态完整。
- 基础设置即时生效。
- 中英文和浅深色满足首版范围。

### 13.2 数据

- 新应用首次启动使用默认设置。
- 新应用在独立目录创建缓存和设置。
- 新应用不读取、迁移、覆盖或删除旧 cc-bar 应用数据。
- 新旧应用可以同时运行。
- 新版缓存损坏时可以安全回退或重建。
- 新版持久化数据包含 Schema Version。
- 若包含本地用量，可以从原始日志完成首次索引。

### 13.3 安全

- Vue 层不接触 Provider 凭据。
- 秘密不写入普通日志、缓存和统计数据。
- macOS 使用独立的系统安全存储 namespace。
- Windows 使用独立的系统安全存储 namespace。
- Tauri capabilities 遵守最小权限原则。

### 13.4 体验

- 新界面不以 Swift 版页面或截图为视觉标准。
- 紧凑入口能优先呈现最重要的额度风险。
- 页面层级、状态反馈和高频操作路径清晰。
- 键盘导航和焦点顺序可用。
- 长内容、中英文和窗口尺寸变化不会破坏布局。
- macOS、Windows 遵循各自系统习惯，同时完成相同核心任务。

### 13.5 工程与发布

- 新应用位于独立仓库。
- 新仓库不包含 Swift / Xcode 工程。
- macOS、Windows 共享主要 Vue 页面、Rust 核心和 contracts。
- 两个平台构建和发布配置相互隔离。
- 新应用拥有独立版本、Release 和安装标识。

## 14. 风险

### 14.1 产品范围重新膨胀

如果把旧版全部功能重新列为首版必须，新仓库仍会退化为一次完整搬运。必须通过 `产品范围.md` 明确首版、后续和不做。

### 14.2 参考旧代码变成复制旧架构

旧实现适合验证规则和边界，不适合直接决定新模块划分。每次引用旧代码时都要说明引用的是业务事实、Fixture 还是平台经验。

### 14.3 首次全量索引

若首版包含本地用量，不能复用旧 Rollup 和 Scan State。大量日志可能导致首次扫描较慢，需要进度、中断恢复和性能验证。

### 14.4 Provider 稳定性

额度接口、凭据位置和 CLI 行为可能变化。新应用仍需具备缓存、错误分类和容错，不能因为是全新应用而降低稳定性。

### 14.5 Windows 环境差异

Windows 的凭据位置、日志路径、CLI 发现、进程参数和系统安全存储需要独立适配和真机验证。

### 14.6 系统区域和 WebView 差异

macOS 使用 WKWebView，Windows 使用 WebView2。系统托盘、字体、滚动、透明窗口、阴影和焦点行为需要分别验证。

### 14.7 品牌和发布关系

如果继续使用 CCBar 名称，必须明确新应用不是无损升级，避免用户误以为旧设置和数据会自动保留。若采用新名称，则需要重新建立产品入口、Release 和说明文档。

### 14.8 双仓库知识漂移

旧仓库与新仓库不能长期维护两套相互矛盾的业务说明。进入新仓库的规则应成为新产品自己的正式文档，旧仓库只保留历史事实。

## 16. 最终结论

新项目应作为独立跨端桌面应用从零开始：

- 新仓库。
- 新应用身份。
- 新数据目录和存储格式。
- 新版本和发布体系。
- 新产品范围。
- 新信息架构、视觉和交互。
- 不迁移、不读取、不删除旧 cc-bar 应用数据。

Codex / Claude Code 自身凭据和原始日志仍可作为外部数据源，但必须通过 Rust 安全边界读取。当前 cc-bar 仓库继续独立保留，只提供已验证的业务事实、Fixture 和问题经验，不作为新应用必须继承的工程或功能清单。

新应用先完成产品定义和双平台最小闭环，再按确认后的价值逐步加入本地用量、对话分析、额度变化、悬浮窗等能力。
