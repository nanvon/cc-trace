# CC Trace 额度领域模型

> 状态：首版基线
> 目标版本：`0.1.x`
> 基线日期：2026-07-25

本文件是 CC Trace 额度业务事实的唯一来源：Provider 协议形态、额度窗口语义、标准化规则、凭据来源和身份变化处理。它是执行清单第 5 阶段的交付物，也是第 12 阶段 Provider 最小闭环的直接输入。

事实来源与边界：

- 业务事实提取自 [cc-bar 只读参考资料](cc-bar-reference/README.md) 第 04 篇，证据等级为“代码已确认”或“测试已确认”。
- 本文件只描述 CC Trace 自己要实现什么，不描述 Swift 版实现结构，也不要求复刻旧版行为。
- 所有协议细节仍需在 Provider 最小闭环中用真实凭据和脱敏 Fixture 复核；静态提取不等于已验证。
- 本文件不记录任何真实 token、邮箱、account id 或本机绝对路径。

状态与错误语义见 [状态与错误模型](状态与错误模型.md)；契约命名、分层与参数基线见 [技术架构](技术架构.md)。

## 1. 领域对象

```text
ProviderIdentity      展示身份：Provider、显示用账号（完整邮箱或 account id）、计划名
QuotaWindow           单个额度窗口
QuotaSnapshot         一个 Provider 在某一时刻的全部额度
ProviderSnapshot      QuotaSnapshot + 三维状态
```

`QuotaWindow` 至少包含：

| 字段 | 含义 | 规则 |
|---|---|---|
| `id` | 窗口稳定标识 | 由 Provider 响应派生，跨刷新稳定，用于匹配旧快照 |
| `kind` | 窗口类型 | 取值见第 2 节，不得由字段名硬编码推断 |
| `displayName` | 展示名 | 可本地化，不参与匹配 |
| `usedPercent` | 已用百分比 | Provider 原值 |
| `remainingPercent` | 剩余百分比 | `clamp(100 - usedPercent, 0, 100)`，统一在 Rust 计算 |
| `resetsAt` | 重置时刻 | 可缺失，缺失时按第 4 节保留规则处理 |
| `windowSeconds` | 窗口长度 | 用于推断 `kind`，可缺失 |
| `isActive` | 是否生效 | 保留 Provider 原始语义，不用于重新排列主次 |
| `isPrimary` | 是否为主数据显示 | 仅第一项为 `true`；是 `windows` 顺序的派生标记，消费方不得据此重新排序 |

## 2. 窗口类型

```text
fiveHour      五小时主窗口
weekly        全模型周窗口
modelWeekly   模型或场景级周窗口
unknown       无法判定
```

**未知窗口必须保留 `unknown`，不得猜成 `fiveHour` 或 `weekly`。** `unknown` 窗口照常展示原始百分比和重置时间，也不能生成推断出的窗口长度；如果它是 Provider 输出的第一项，仍作为主数据显示，但窗口类型继续显示为 `unknown`。

首版的额度分层：

| 层级 | 定义 | 来源 |
|---|---|---|
| 主要额度 | Provider 标准化输出的 `QuotaSnapshot.windows[0]`，不再按 `kind` 或 `isActive` 二次选择 | 紧凑面板第一行、主窗口第一行与系统区域数字的共同来源 |
| 次级额度 | `windows[1...]`，保持 Provider 输出顺序 | 显示在主数据下方 |

主次由 Provider 输出顺序决定，不根据「5 小时」「每周」等展示名重新排序，也不为 Codex、Claude Code 写展示层特判。Codex 当前只有 weekly 时，weekly 自然成为第一项；Claude Code 同时返回 session 与 weekly 时，session 位于第一项。

## 3. Provider 协议

以下形态提取自旧版已验证实现，首版按同一语义重新实现，不复制旧代码结构。请求由 Rust 发出，Vue 不接触端点、请求头和响应原文。

### 3.1 Codex

```text
GET https://chatgpt.com/backend-api/wham/usage
Authorization: Bearer <access token>
Accept: application/json
User-Agent: codex-cli
ChatGPT-Account-Id: <OAuth account id>
```

响应映射：

| 响应内容 | 映射 |
|---|---|
| `plan_type` | `ProviderIdentity.plan` |
| `rate_limit.primary_window` | 标准化后放进 `windows[0]`，作为主数据；仍按 `limit_window_seconds` 判定窗口类型 |
| `rate_limit.secondary_window` | 次要窗口，可缺失 |
| 每个窗口的 `used_percent`、`reset_at`、`reset_after_seconds`、`limit_window_seconds` | `QuotaWindow` 对应字段 |
| 响应内的 account 与 email 字段 | 用于身份变化判断；作为展示账号经 `ProviderIdentity.account` 传给前端（见 [ADR-0025](决策/ADR-0025-非隐私模式显示完整邮箱.md)） |

`limit_window_seconds` 缺失或无法判定时，`kind` 为 `unknown`。

### 3.2 Claude Code

```text
GET https://api.anthropic.com/api/oauth/usage
Authorization: Bearer <access token>
anthropic-beta: oauth-2025-04-20
```

响应映射：

| 响应内容 | 映射 |
|---|---|
| `limits[].session` | `fiveHour` |
| `limits[].weekly_all` | `weekly` |
| `limits[].weekly_scoped` | `modelWeekly`，`id` 与 `displayName` 由 scope 的模型或场景派生 |
| legacy `five_hour`、`seven_day`、`seven_day_opus`、`seven_day_sonnet` | 分别并入上述语义窗口 |
| 各窗口的百分比、reset 与 is_active | `QuotaWindow` 对应字段 |

同一语义窗口同时出现在 legacy 与新字段时合并为一个 `QuotaWindow`，不重复展示。
标准化输出顺序固定为 session、weekly、modelWeekly、unknown；实际存在的第一项就是主数据。

### 3.3 首版不实现

- Codex Reset Credits 查询。
- Claude Code CLI 交互式额度兜底（`ClaudeCLIFallbackQuotaClient` 等价能力）。
- Claude Code delegated refresh：通过外部 CLI、PTY 或 watchdog 触发的受信任刷新。
- Antigravity 及任何第三个 Provider。

CLI 兜底与 delegated refresh 需要启动外部进程、PTY 和看门狗，与首版“权限克制”原则冲突，因此明确不做，见 [ADR-0007](决策/ADR-0007-首版不实现CLI兜底与delegated-refresh.md)。

OpenAI 与 Anthropic 公开 Statuspage 状态链已由 [ADR-0026](决策/ADR-0026-Statuspage状态链进入首版.md) 纳入首版，但**Provider quota 失败与 Statuspage 故障是两条独立状态链，不得合并**：Statuspage 报告官方服务的公开故障，三维状态报告本机凭据与请求结果；服务状态不进 `ProviderAvailability`、不进 Overall Signal、不参与退避与刷新调度。

## 4. 标准化与快照规则

- `remainingPercent` 统一 clamp 到 `0–100`，不在 Vue 重新计算。
- `QuotaSnapshot.windows` 的顺序具有展示语义：第一项同时驱动卡片主行与系统区域数字，其余项按原顺序显示在下方。
- `isPrimary` 只是第一项的派生标记；前端和系统区域不得按窗口类型或旧缓存里的 `isPrimary` 重新选择。
- 窗口匹配使用 `id` 与 `kind`，不使用展示名或数组下标。
- **reset 保留：** 新快照中某窗口缺少 `resetsAt`，而旧快照同一窗口的 `resetsAt` 仍在未来时，沿用旧值，并保持该窗口的新鲜度标记与其余数据一致。
- 刷新失败不清空最后一份可展示快照。
- 快照只保存展示数据（身份含完整账号，见 [ADR-0025](决策/ADR-0025-非隐私模式显示完整邮箱.md)），不保存凭据、原始响应或请求头。
- 每个 Provider 独立维护自己的快照与刷新状态。

### 4.1 身份变化

Provider 身份（account id 或 email）与上一次成功刷新不一致时，必须：

1. 丢弃该 Provider 的既有快照与缓存条目。
2. 清除该 Provider 的退避状态。
3. 按新身份重新获取，期间界面不得展示上一个身份的额度。

身份比较只在 Rust 内进行，比较值**从不落盘**：实现使用**单向摘要**（account id 与邮箱的
SHA-256 前 16 个十六进制字符），摘要写进 `quota-cache.json`，因此重启后的第一次刷新也能
发现身份变化。展示身份（完整账号）按 [ADR-0025](决策/ADR-0025-非隐私模式显示完整邮箱.md)
进入 command 载荷与缓存，但不得进入日志与错误文案。

判定规则与已知限制：

- 任一侧算不出摘要时**不做丢弃**：「无法比较」不等于「变了」，误丢一份有效快照比多显示一次更糟。
- Codex 的摘要取自 account id 与邮箱，Claude Code 只有邮箱可用。
- > 待确认：Claude Code 的邮箱可能来自 `~/.claude.json` 兜底。若用户换了账号而该文件未同步更新，或凭据与该文件都没有邮箱，身份变化将无法检测，界面会短暂显示上一个身份的额度直到下次刷新覆盖。实机验证时需要确认真实凭据是否稳定携带可用于识别身份的字段。

## 5. 凭据来源

| Provider | 首版读取来源 | 说明 |
|---|---|---|
| Codex | `CODEX_HOME/auth.json`，未设置时 `~/.codex/auth.json` | 仅使用 OAuth 凭据 |
| Claude Code（macOS） | `~/.claude/.credentials.json`；缺失、为空或无法解析时读取 Keychain generic password `Claude Code-credentials` | 见 [ADR-0013](决策/ADR-0013-macOS读取ClaudeCode钥匙串凭据.md)；显示用邮箱可由 `~/.claude.json` 兜底 |
| Claude Code（Windows） | `~/.claude/.credentials.json` | 不读取 Windows Credential Manager；无验证主机，不凭空实现 |

**两个平台的 Claude Code 凭据来源不一致**，这是 [ADR-0013](决策/ADR-0013-macOS读取ClaudeCode钥匙串凭据.md) 明确接受的代价。Keychain 使用系统 API 读取，不启动 `security` 子进程。首次读取会触发一次系统钥匙串授权弹窗。

规则：

- 不创建、不删除外部凭据来源；除 token 刷新结果外不修改其内容，见 [ADR-0014](决策/ADR-0014-token刷新结果回写外部凭据.md) 与第 5.2 节。
- 凭据只在完成请求所需的生命周期内存在于 Rust 内存。
- 文件缺失或无可用凭据 → `no_credentials`。
- 文件存在但内容无法识别、或只含首版不支持的凭据形式 → `unsupported`，并给出可理解说明。
- Windows 与 macOS 使用同一套文件来源，路径差异由平台适配层解析。

### 5.1 首版凭据决策

| 决策 | 内容 | 理由 |
|---|---|---|
| 只支持 Codex OAuth | 只含 PAT 的 `auth.json` 报 `unsupported` | PAT 无 JWT 与 refresh，身份要靠额外请求回填；首版不提供账号导入与编辑，见 [ADR-0006](决策/ADR-0006-首版只支持Codex-OAuth凭据.md) |
| macOS 读取 Keychain | Claude Code 文件缺失时回退到系统钥匙串 | 2026-07-27 核对确认凭据只在 Keychain 的机器确实存在，只读文件会把有效登录态误判为 `no_credentials`，见 [ADR-0013](决策/ADR-0013-macOS读取ClaudeCode钥匙串凭据.md) |

Keychain 读取失败（用户拒绝授权、项被删除）落在 `no_credentials` 或凭据类 `error`，不得降级成 `offline`。

### 5.2 Token 刷新

| 参数 | 首版值 | 说明 |
|---|---|---|
| Codex 刷新提前量 | access token 距过期少于 `300` 秒 | 过期时刻取自 access token 的 JWT `exp`，只解 payload 不验签 |
| Claude Code 刷新提前量 | access token 距过期少于 `30` 秒 | 与旧版已验证值一致，不使用泛化的 5 分钟 |
| 并发 | 同一 Provider 进程内只允许一个刷新任务 | 其余调用等待同一结果 |
| 外部变化 | 刷新前重新读取凭据来源 | 其他客户端已写入更新的 token 时直接采用，不发请求 |
| 回写 | 续期成功后原子回写读取它的**同一个来源** | 见下方规则与 [ADR-0014](决策/ADR-0014-token刷新结果回写外部凭据.md) |
| 失败 | 刷新失败归为凭据类 `error`，不伪装成 `offline` | 见 [状态与错误模型](状态与错误模型.md) |

回写规则：

- 只更新 access token、refresh token、过期时刻与 Provider 自有刷新元数据（Codex
  `last_refresh`），保留 payload 中其余字段。
- Codex 写 `auth.json`；Claude Code 写它实际读到的那个来源（文件或 macOS Keychain 项）。
- 回写前必须重新确认来源仍存在、可读且保持受支持的 OAuth 结构；任一条件不满足就失败，
  不创建新文件、不把损坏内容替换成最小 payload。
- 回写时必须确认 access token、refresh token 与账号来源仍是发起刷新时的版本；若外部
  CLI 已轮换或切换账号，放弃本次回写并按凭据类 `error` 处理；后续刷新重新发现完整
  凭据，不混用新 token 与旧身份。
- macOS Keychain 只原位更新已经匹配到的 Claude Code 条目；条目或精确 account 消失时
  失败，不用登录用户名兜底，也不新建条目。
- 使用临时文件写入并原子替换，保留原有权限位；写入失败时保留原文件，并把本次刷新按凭据类 `error` 处理。
- 刷新被服务端拒绝（`invalid_grant`）时，等待一次并重读来源；发现其他客户端已写入新 token 就静默采用，否则报凭据类 `error`。首版不实现 delegated refresh，见 [ADR-0007](决策/ADR-0007-首版不实现CLI兜底与delegated-refresh.md)。

**回写是 refresh token 轮换语义的必然要求**：Claude Code 的 refresh token 会轮换，刷新后不回写会作废用户 CLI 手里的那份，导致 Claude Code 掉登录。这是 [ADR-0014](决策/ADR-0014-token刷新结果回写外部凭据.md) 局部推翻第 4 阶段「不写回外部凭据文件」数据边界的原因；该边界的其余部分（不创建、不删除、不写入刷新结果与 Provider 自有刷新元数据之外的字段）仍然有效。
