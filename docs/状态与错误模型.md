# CC Trace 状态与错误模型

> 状态：首版基线
> 目标版本：`0.1.x`
> 基线日期：2026-07-25

本文件是 CC Trace 展示状态、失败原因、退避与重试语义的唯一来源。产品范围、信息架构、设计方向和技术架构只引用本文件，不重复定义状态集合。

分工：

- 本文件定义状态的**语义**与**转换规则**。
- 各表面展示哪些状态见 [信息架构与核心流程](信息架构与核心流程.md)。
- 状态的**视觉表达**见 [设计方向与状态规范](设计方向与状态规范.md) 第 8 节。
- 状态的**契约命名与序列化**见 [技术架构](技术架构.md)。
- Provider 侧的错误来源见 [额度领域模型](额度领域模型.md)。

## 1. 三个维度

首版不把所有情况压成一个互斥状态。每个 Provider 的展示状态由三个独立维度组成：

| 维度 | contract | 取值 | 回答的问题 |
|---|---|---|---|
| 活动 | `RefreshState` | `idle`、`loading`、`refreshing` | 现在是否正在工作？ |
| 快照新鲜度 | `SnapshotFreshness` | `empty`、`live`、`stale` | 当前展示的数据是否可信、是否为旧数据？ |
| 可用性／失败原因 | `ProviderAvailability` | `ready`、`no_credentials`、`unsupported`、`offline`、`rate_limited`、`error` | 为什么能或不能取得新数据？ |

硬规则：

- 三个维度必须各自独立序列化，不得合并成一个互斥枚举。
- 前端不得通过空值、`null` 或空数组推断状态。
- `no_credentials`、`unsupported`、`rate_limited` 不得降级成普通 `error`。
- 已有快照不得因为开始刷新而被清空。
- 旧快照不得因为仍有数值而被标记为成功。

## 2. 组合矩阵

| 场景 | 活动 | 快照 | 原因 |
|---|---|---|---|
| 等待用户首次检查 | `idle` | `empty` | `ready` |
| 首次加载 | `loading` | `empty` | `ready` |
| 有快照并刷新 | `refreshing` | `live` 或 `stale` | `ready` |
| 刷新成功 | `idle` | `live` | `ready` |
| 无凭据 | `idle` | `empty` | `no_credentials` |
| 凭据形式不支持 | `idle` | `empty` | `unsupported` |
| 离线且有快照 | `idle` | `stale` | `offline` |
| 离线且无快照 | `idle` | `empty` | `offline` |
| 429 且有快照 | `idle` | `stale` | `rate_limited` |
| 429 且无快照 | `idle` | `empty` | `rate_limited` |
| 协议或凭据错误且有快照 | `idle` | `stale` | `error` |
| 协议或凭据错误且无快照 | `idle` | `empty` | `error` |
| 快照过期未能刷新 | `idle` | `stale` | 保持上一次的失败原因 |

## 3. 状态优先级

同一 Provider 同时存在多个信号时，按以下顺序决定用户首先看到的内容：

1. 安全或凭据问题（`no_credentials`、`unsupported`、凭据类 `error`）。
2. 无快照的失败。
3. 有快照但无法刷新。
4. 正在刷新。
5. 当前实时额度。

总体状态只提高最高风险的视觉权重，不改变 Provider 的空间顺序。

## 4. 失败原因分类

Provider 请求失败必须映射到明确的 `ProviderAvailability`，不允许出现兜底的“未知错误”作为用户解释。

| 失败来源 | `ProviderAvailability` | 说明 |
|---|---|---|
| 凭据文件缺失或无可用凭据 | `no_credentials` | 不发起请求 |
| 凭据存在但形式不受首版支持 | `unsupported` | 不发起请求，说明支持范围 |
| 无网络、DNS 失败、连接被拒 | `offline` | 明确的网络不可达 |
| 请求超时、传输中断 | `offline` | 归为网络类失败 |
| HTTP 429 | `rate_limited` | 进入退避，提供可再次尝试时间 |
| HTTP 401、403、token 刷新失败或被吊销 | `error` | 凭据类错误，不得伪装成离线 |
| 其他 HTTP 状态、响应无法解析、字段不兼容 | `error` | 协议类错误 |

- 凭据类与协议类错误必须在用户可见文案中区分：前者指向“在对应 CLI 重新登录”，后者指向“稍后重试或升级 CC Trace”。
- 失败原因不携带 HTTP 原文、Rust 枚举名、文件路径或凭据内容。

## 5. 退避与重试

| 规则 | 内容 |
|---|---|
| 独立性 | 每个 Provider 独立计算退避，一个 Provider 的退避不影响另一个 |
| 429 | 优先使用服务端 `Retry-After`；缺失时按 [技术架构](技术架构.md) “首版参数基线” |
| 网络与临时错误 | 按参数基线的递增退避 |
| 凭据类与协议类 `error` | 同样进入退避，沿用「网络与临时错误」阶梯。持续失败时自动刷新不得反复打 Provider |
| **手动刷新不得绕过退避** | 退避期内的手动刷新不发起真实请求；界面给出限流反馈：状态点 tooltip 的「可再试」与刷新按钮 `title`（见 [设计方向与状态规范](设计方向与状态规范.md) 第 7.4 节） |
| 请求合并 | 同一 Provider 的并发刷新合并为一个任务 |
| 退避解除 | 一次成功刷新后重置该 Provider 的退避 |
| 身份变化 | 清除该 Provider 的退避，见 [额度领域模型](额度领域模型.md) 第 4.1 节 |

退避期内界面必须保持可操作：用户可以关闭面板、打开主窗口并在其中进入设置，不被阻塞。

## 6. 快照新鲜度

- `live`：本次刷新成功，且快照年龄未超过降级阈值。
- `stale`：刷新失败后保留的上一份有效快照，或快照年龄超过阈值而尚未成功刷新。
- `empty`：没有可展示的快照。

降级阈值与启动、唤醒时的刷新时机见 [技术架构](技术架构.md) “首版参数基线”。快照降级为 `stale` 时保留原有数值与重置时间，只改变新鲜度标记与说明。

## 7. 禁止事项

- 不把 `no_credentials` 显示成 `0%` 或空额度。
- 不用旧快照冒充刷新成功。
- 不用单一灰色圆点表达离线。
- 不只用颜色表达状态；必须同时有状态词、图形或说明。
- 不在退避期内持续发起请求。
- 不因为一个 Provider 失败而隐藏另一个 Provider 的成功结果。
- 不为状态引入第二套并行来源。
