## 1. 本地环境

| 依赖 | 要求 |
|---|---|
| Node.js | 22 或更高 |
| pnpm | 11（`packageManager` 已固定具体版本） |
| Rust | 当前稳定工具链 |
| 平台依赖 | 见 [Tauri prerequisites](https://v2.tauri.app/start/prerequisites/) |
| 最低运行平台 | macOS 13、Windows 10 22H2（系统 WebView2） |

`src-tauri/tauri.conf.json` 已声明 `bundle.macOS.minimumSystemVersion = "13.0"` 与 `bundle.windows.webviewInstallMode = downloadBootstrapper`。

### 1.1 macOS 开发期代码签名

macOS 上读取 Claude Code 的钥匙串凭据需要一次性授权，而 cargo 产出的 adhoc 签名没有稳定标识，钥匙串 ACL 只能按 CDHash 记录，每次重新编译都会重新索要授权。背景见 [ADR-0013](决策/ADR-0013-macOS读取ClaudeCode钥匙串凭据.md)。

`src-tauri/.cargo/config.toml` 因此给 macOS 配了 cargo runner `scripts/dev-sign.sh`：`cargo run`（`pnpm tauri dev` 走的就是它）在启动二进制前先用固定身份重新签名，并把签名标识钉死成 `tauri.conf.json` 里的 `identifier`。

| 项 | 取值 |
|---|---|
| 签名身份 | `CC_TRACE_SIGN_IDENTITY` 优先，否则取第一个有效的代码签名身份 |
| 签名标识 | `src-tauri/tauri.conf.json` 的 `identifier`，当前为 `com.nanvon.cctrace` |
| 无签名身份时 | 跳过签名并继续运行，只在 stderr 提示 |
| 非 macOS 与 `deps/` 下的测试二进制 | 直接放行，不签名 |

首次运行时系统会弹一次钥匙串授权，**必须点「始终允许」**；点「允许」只放行当次，不写入 ACL。授权一次后重新编译不再弹窗。

签名身份使用免费 Apple ID 通过 Xcode 取得的 Apple Development 证书即可，不需要付费开发者账号，见 [ADR-0016](决策/ADR-0016-不购买Apple开发者账号.md)。

| 命令 | 作用 |
|---|---|
| `pnpm install` | 安装前端依赖 |

## 3. CI 基线

首版 CI 只保证“代码能编译、类型正确、格式与 lint 通过、测试通过”，不承担打包与发布。

| 项 | 首版值 |
|---|---|
| 平台 | GitHub Actions |
| 触发 | 向 `main` 的 push 与 pull request，以及手动触发 |
| 运行环境 | `macos-latest` 与 `windows-latest` 两个 job |
| 前端步骤 | `pnpm install --frozen-lockfile` → `pnpm lint` → `pnpm build` → `pnpm test` |
| Rust 步骤 | `cargo fmt --check` → `cargo clippy --all-targets -- -D warnings` → `cargo test` |
| 缓存 | pnpm store、Cargo registry 与 `target/` |
| 失败策略 | 任一 job 失败即失败；两个平台都必须通过 |

CI 明确不做：

- 不执行 `tauri build`、不产出安装包、不签名、不公证、不创建 Release。
- 不发起任何真实 Provider 请求，也不注入凭据；Provider 相关测试只用脱敏 Fixture。
- 不依赖相邻的 `../cc-bar` 仓库存在。
- 不运行需要真实桌面会话的 Tray、窗口或多显示器验证；这些属人工实机验证，见 [桌面壳验证记录](桌面壳验证记录.md)。

CI 配置已建立：`.github/workflows/ci.yml`。它不引用 `../cc-bar`，也不执行任何真实 Provider 请求。

### 3.1 GitHub Release 自动打包

发布打包与日常 CI 分离，由 `.github/workflows/release.yml` 负责。推送 `v*` tag 后：

1. `scripts/check-release-version.mjs` 校验 tag 与三处应用版本完全一致。
2. 两个 macOS job 都显式选择 Xcode 26 并校验 macOS SDK 主版本为 26，不依赖 runner
   镜像可能变化的默认 Xcode；这只决定编译 SDK，最低运行版本仍为 macOS 13。
3. 在 GitHub 托管 runner 上分别构建三个安装包：
   - macOS Apple Silicon：`macos-15`／`aarch64-apple-darwin` DMG；
   - macOS Intel：`macos-15-intel`／`x86_64-apple-darwin` DMG；
   - Windows x64：`x86_64-pc-windows-msvc` NSIS EXE。
4. 创建同 tag 的 **Draft Release**，使用 GitHub 自动生成的 Release Notes 上传三个产物。
5. 下载 Draft Release 的全部产物，生成并上传 `SHA256SUMS.txt`。

macOS workflow 显式使用 `APPLE_SIGNING_IDENTITY=-` 做 ad-hoc 签名，不需要任何 Apple
证书、私钥或账号 Secret；Windows 产物不做代码签名。签名理由与用户影响见
[ADR-0016](决策/ADR-0016-不购买Apple开发者账号.md)。

Release workflow 只负责可重复打包，不替代第 3 节 CI，不注入 Provider 凭据、不发起真实
Provider 请求，也不等于平台实机验收。第 16 阶段完成前保持 Draft，由产品所有者人工检查后
再决定是否公开。

## 4. 版本规则

- 开发阶段使用 `0.x`，首个正式版为 `1.0.0`。
- 版本号在三处出现且必须完全一致：`package.json`、`src-tauri/Cargo.toml`、`src-tauri/tauri.conf.json`。当前三处均为 `0.1.0`。
- 改版本号时三处一起改；Release workflow 会校验三处版本号与 `v<version>` tag，一处不一致就停止打包。
- 持久化数据的 `schemaVersion` 与应用版本相互独立，不跟随版本号变化，见 [技术架构](技术架构.md)。

## 5. 发布边界

- **不购买 Apple 开发者账号，因此不做公证**，见 [ADR-0016](决策/ADR-0016-不购买Apple开发者账号.md)。
- macOS 开发期使用第 1.1 节的 Apple Development 证书稳定钥匙串 ACL；GitHub 公开发布产物改用 ad-hoc 签名，不上传个人证书或私钥。这两种签名承担不同职责。
- ad-hoc 产物不受 Gatekeeper 信任；安装新版本后，因为 CDHash 变化，首次读取 Claude Code 钥匙串凭据时可能需要再次选择「始终允许」。
- Windows 不购买代码签名证书，NSIS EXE 未签名，会触发 SmartScreen 或 Unknown Publisher 提示。该行为尚未实机验证。
- 源码仓库计划公开；`0.x` 安装包先作为测试发布。用户首次打开会遇到 Gatekeeper 或 SmartScreen，发布说明必须写明这是预期行为并给出打开方法。
- 两个平台的安装器已配置自动构建；自动更新仍在公开分发前单独设计与验收，不进入首版开发流程。
- macOS 与 Windows 分别构建平台产物，不做跨平台交叉打包假设。
- 首版发布说明必须明确：CC Trace 不是 Swift 版 cc-bar 的无损升级，不迁移旧设置、缓存与账号，也不会自动卸载或清理旧应用，见 [ADR-0003](决策/ADR-0003-独立应用身份不迁移数据.md)。
- 旧 cc-bar 的维护或归档计划在 CC Trace 发布之后再决定。

## 6. 发布检查单

首个公开版本发布前逐项确认：

- [ ] 逐项对照 [产品范围](产品范围.md) 的“首版完成标准”，没有遗漏，也没有把后续能力带入首版。
- [ ] [测试策略](测试策略.md) 第 7 节的最低门槛全部满足。
- [ ] macOS 与 Windows 各完成一次实机验收并写入验证记录。
- [ ] 三处版本号一致，且与 Release 标签一致。
- [ ] 文档与实现值同步：窗口尺寸、色值、参数基线、command 与 event 清单。
- [ ] 日志脱敏测试通过，产物中无秘密写入路径，见 [日志与诊断](日志与诊断.md)。
- [ ] 中英文文案完整，无死 key、无硬编码语言，见 [文案与国际化](文案与国际化.md)。
- [ ] 新旧应用并行运行互不影响，已审计数据目录与安全存储隔离。
- [ ] GitHub Actions 已实际产出 Apple Silicon DMG、Intel DMG 与 Windows x64 NSIS EXE。
- [ ] 两个 macOS DMG 均确认是 ad-hoc 签名，并在对应架构真机验证安装、Gatekeeper 放行与升级后的钥匙串授权。
- [ ] Windows NSIS EXE 已在 Windows 10 22H2 与目标 Windows 11 环境验证安装、SmartScreen、启动和卸载。
- [ ] `SHA256SUMS.txt` 与三个 Release 产物逐一匹配。
- [ ] 发布说明已写明 Gatekeeper／SmartScreen 提示是预期行为，并给出打开方法。
- [ ] GitHub 自动生成的 Release Notes 已检查，能准确概括用户可感知变化。
- [x] 许可证已确定（MIT）。
