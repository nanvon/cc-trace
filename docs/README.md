# CC Trace 文档地图

本目录是 CC Trace 的产品与工程文档。本文件说明每份文档的职责、**每个事实由谁拥有**，以及修改文档时必须遵守的规则。

开始任何工作前，先在下面的所有权表里找到相关事实的所有者，读那一份文档；不要凭多份文档的相似段落拼凑结论。

### 为什么有四份文档在仓库根目录

- `README.md`：仓库入口，必须在根。
- `AGENTS.md`：AI 协作约定读取仓库根；`CLAUDE.md` 是它的符号链接。
- `PRODUCT.md`、`DESIGN.md`：`impeccable` 的上下文文件。解析顺序是项目根 → `.agents/context/` → `docs/`；规范位置是项目根，且两份文件必须放在同一目录，只移动其中一份会导致另一份被判定为不存在。

## 4. 修改规则

1. **先找所有者。** 要改的事实由哪份文档拥有，就改那一份；其他文档如果重述了同一取值，改成引用而不是同步两份。
2. **实现值与文档值双向同步。** 窗口尺寸、色值、参数基线在代码里有真值，改代码必须同时改文档，改文档必须同时改代码，不允许只改一侧。
3. **决策进 ADR。** 新增或推翻一个决策时，写或更新对应 ADR，规范文档里只留结论。推翻既有决策是正常操作，不是例外：任何 ADR 都可以在有更好方案时被推翻，判断依据是方案本身的代价，不是「文档已经定了」。协作层面的完整规则见 `AGENTS.md` 第 1 节「文档的效力」。
4. **验证结果不写进规范。** 实机结果、浏览器验证、抽样结论写进验证记录，并标注平台与日期；未验证的平台明确写未验证。
5. **待确认要显式标注。** 无法确定的取值写成“> 待确认”，并说明如果假设错误会影响什么，不要用看起来确定的语气蒙过去。
6. **归档而不是删除。** 过期的规划文档移入 `archive/` 并在顶部注明冲突时以哪份文档为准。
